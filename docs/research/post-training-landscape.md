# Post-training landscape

Research date: 2026-09-06. Dew revision: `65fd2f4`.

This note covers methods, rollout systems, agent environments, model reports, and data contracts. It makes fit recommendations. It does not select an implementation or change an API.

Dew's baseline comes from the source files cited below. The starting documents were `docs/design/post-training.md:17-149`, `docs/concepts/post_training.md:5-116`, `README.md:69-77`, and `CONTRIBUTING.md:5-19`. Some statements in the design document exceed the current implementation. Those differences are recorded below. The older survey in `docs/research/frontier-training.md:20-32,203` describes an earlier Dew and is not the baseline for this note.

Paper citations name a version and section. Repository snapshots are listed under Sources. Live documentation and model cards were read on the research date. A report's result is evidence about that report's experiment. It is not a guarantee for Dew. “Not disclosed” means the inspected primary sources do not supply the detail. “Nothing” means there is no corresponding capability in the inspected Dew paths.

## Methods and their mathematical differences

Let `mu` be the policy that actually sampled an action. Let `pi_old` be a recent training-policy snapshot and `pi` the policy being updated. Let `A` be an advantage and `m` the model-action loss mask. These roles can coincide in a synchronous run. They differ in asynchronous training and when sampling and training engines disagree. [AReaL §5.2][areal-paper] and [SkyRL's correction guide][skyrl-correction] keep these distinctions explicit.

RLVR describes the source of reward. It does not prescribe GRPO. Tülu 3 names RLVR and uses PPO with a value model. DeepSeek-R1 uses GRPO with verifiable accuracy and format rewards in its reasoning stages. [Tülu 3 §6][tulu3], [Open Instruct][open-instruct], [DeepSeek-R1 §2][r1], [R1 repository][r1-repo].

## KL, length, and reward contracts

For `d = log(pi_ref) - log(pi)`, k1 is `-d`, k2 is `d*d/2`, and k3 is `exp(d)-d-1`. Unclamped k1 and k3 estimate `KL(pi || pi_ref)` when actions are sampled from `pi`. k2 is a biased local approximation. Sampled k1 can be negative. k3 is nonnegative per token. These are value-estimator statements. Differentiating a sample estimator on old-policy data is a separate issue. [Schulman's derivation][kl], [DeepSeek-V3.2 §3.1][ds32].

## Multi-turn agents and execution environments

A model action can contain reasoning, visible text, tool-call names, and tool arguments. Tool results are observations. They remain available as context but receive zero policy-gradient weight unless a separately specified auxiliary objective trains on observations. Repeated prompt prefixes also must not be counted again as new actions. Context compaction can replace the prefix entirely. The exact input to each model call is then the training state. [SkyRL-Agent §2][skyagent], [M2 §6.1.1-6.1.3][m2], [GLM-5 §4.1.2][glm5].

The training loop needs the model-call inputs and sampled token outputs, tool-call/result boundaries, per-turn action masks, parent/child episode identity, termination reason, reset identity, and tests or judge evidence. These follow from the mask/transition split in [SkyRL-Agent][skyagent], gateway capture in [rLLM][rllm], and task/verifier separation in [Harbor][harbor-tasks].

The agent executor needs a serving endpoint with the model's tool and thinking format, sampling limits, model version, cancellation/pause behavior, and completion status. It needs the trainer to publish weights atomically and declare whether an episode may cross versions. It also needs capacity control so environment leases do not expire behind an unbounded inference queue. The reference examples are [AReaL][areal-paper], [Tunix's rollout contract][tunix-rollout], and [K3's partial rollout system][k3]. An executor does not need optimizer internals.

| Reproducible environment state | [E2B][e2b], [Daytona][daytona], [K3][k3], and [V4][dsv4]. | Nothing. | Need image/task digest, reset seed, sandbox ID, durable checkpoint or restart policy, tool request IDs, and artifact references. | Host-only rollout state coordinated with checkpoints. Logs, secrets, and large artifacts must not be encoded as padded device strings. |

## What dew needs

1. Exact sampling and scoring semantics. Preserve sampled tokens and behavior log-probabilities. Resolve padding, EOS, reward truncation, and generation/scorer agreement before scaling the current sampler. Evidence: `src/dew/objectives/rl/rollout.py:100-153`, `src/dew/sampling/text.py:16-48`, [V3.2 §3.1][ds32], [TRL][trl-grpo]. Fit: `Rollout`, generation, and the objective's per-token scoring seam.
2. A lossless episode/transition record with an array training view. Preserve tool calls/results, roles/channels, per-call context, action masks, group identity, and compaction lineage. Evidence: `src/dew/data/chat.py:50-84`, [rLLM][rllm], [SkyRL-Agent][skyagent]. Fit: data transforms and `Rollout`; only the compiled view crosses `Objective.loss`.
3. Multi-host rollout ownership and independent serving placement. Establish which process owns prompts, returned groups, and engine synchronization. The current globally sharded input followed by NumPy conversion is not a process-local contract. Evidence: `src/dew/training/distributed.py:335-340,379-402`, `src/dew/training/trainer.py:485-495`, [Tunix][tunix-design], [HybridFlow][hybridflow]. Fit: trainer capabilities plus `MeshSpec`/`Layout` for training placement; serving placement remains explicit.
4. Versioned weight publication to real inference engines. Include model-family mapping, complete-update acknowledgement, cache policy, and sampler probability output. Evidence: `src/dew/interop/hf_decoders.py:2068-2125,2279-2302`, [Tunix][tunix-rollout], [SkyRL][skyrl-sync]. Fit: `DecoderFamily` for weight vocabulary and a host capability beside `Rollout`. Engine-specific optimized attention remains behind `attention_impl`; a loss choice does not belong there.
5. Sandboxed executable verifiers and environment reset. Keep test/solution state outside the agent's writable workspace. Distinguish test failure, invalid output, timeout, and verifier failure. Evidence: scalar-only `src/dew/objectives/rl/rollout.py:28-31,119-123`, [SWE-Gym][swe-gym], [Harbor][harbor-tasks], [Docker][docker]. Fit: optional host environment/reward adapters called by `Rollout`.
6. Explicit estimator and surrogate compositions. Add the complete contracts for Dr. GRPO, GSPO, CISPO, GMPO, REINFORCE++, and original RLOO. Preserve the existing primitives and name their reduction and gradient rules. Evidence: `src/dew/rl/advantage.py:100-170`, `src/dew/rl/surrogate.py:83-170`, and the method papers above. Fit: `dew.rl` and `Objective`; collection-dependent normalization belongs at the appropriate batch boundary.
7. Dynamic collection, credit assignment, and curriculum. Support useful-group replacement, overlong policies, per-turn reward-to-go, task mixtures, and explicit episode termination. Evidence: fixed collection in `src/dew/objectives/rl/rollout.py:112-151`, [DAPO][dapo], [M2][m2], [verl-agent][verl-agent]. Fit: `Rollout` preparation plus objective reductions. A curriculum is host data policy, not model architecture.
8. Asynchronous admission and off-policy correction. Retain behavior and proximal scores separately. Support a declared staleness policy and the selected IS/masking rule. Measure mismatch, effective sample size, rejection, and task-mixture drift. Evidence: `src/dew/training/trainer.py:485-505`, [AReaL][areal-paper], [PipelineRL][pipeline-paper], [SkyRL][skyrl-correction]. Fit: stateful host rollout capability and `dew.rl`. A queue with stale rescored probabilities does not fit the existing on-policy assumptions.
9. Episode-aware checkpoint and failure recovery. Persist consumed data identity, outstanding groups, sampled prefixes/probabilities, tool request status, and sandbox restoration state. Coordinate these with published policy versions. Evidence: `src/dew/training/state.py:14-28`, `src/dew/training/trainer.py:549-561`, [V4][dsv4], [K3][k3], [TRL async][trl-async]. Fit: trainer checkpoint capability and host rollout state. Blanket resampling of interrupted jobs does not preserve the original sampling distribution.
10. Teacher scoring and on-policy distillation. Support one or more independently versioned teachers on student-generated states. Specify same-tokenizer alignment first. Evaluate sampled-token and full-vocabulary objectives as different methods. Evidence: selected-token-only `src/dew/objectives/lm/objective.py:345-349`, [Qwen3][qwen3], [V4][dsv4], [K3][k3]. Fit: host teacher capability, `Objective`, and recipes. Several teachers do not fit one frozen EMA slot.
11. A critic-capable single-rollout path. Add value learning and a defined actor/value update schedule if Tülu-style PPO or GLM SAO is a target. Evidence: GAE without a critic at `src/dew/rl/advantage.py:133-170`, [Tülu 3][tulu3], [SAO][sao]. Fit: objective-owned trainable state and the trainer's update capability. An environment call inside the custom compiled step does not fit.
12. Reward-model and judge training workflows. Add outcome/process scoring, rubric provenance, and calibration against held-out verifiable results. Evidence: `src/dew/objectives/rl/rollout.py:28-31`, [Qwen3][qwen3], [PRM800K][prm-data], [K2][k2]. Fit: objectives for learned scorers; host reward services for evaluation. Keep value prediction, process judgment, and task verification distinct.
13. Reproducible stage and evaluation recipes. Supply text decoding/EOS to the current chain; add expert-data generation, rejection sampling, and distillation stages as their capabilities become available. Evaluate task success and retention, not just prompt perplexity. Evidence: `recipes/chain.py:116-134`, `src/dew/objectives/rl/grpo.py:124-155`, [R1][r1], [GLM-4.5][glm45], [Tülu 3][tulu3]. Fit: recipes, data, objectives, and existing telemetry/checkpoint capabilities.

Remote generation, tools, sandbox lifecycle, and judge RPCs do not fit inside `jit` or `Objective.loss`. Pure local generation already uses its own compiled scan; the restriction concerns host effects and the trainer's compiled update. `src/dew/training/trainer.py:59-68,401-414` and `src/dew/sampling/text.py:28-48,71-74` establish that split. `Process` is a diffusion schedule/prediction/weighting value (`src/dew/diffusion/process.py:19-38`); it is not an agent-process manager. Model architecture and weight conversion belong to `DecoderFamily`. Attention kernels belong to `attention_impl`. Neither should own rewards, task resets, or rollout queues.

## Open questions for the owner

1. Which first acceptance workload matters most: single-turn math/code RLVR, repository-editing agents, or long-running multi-agent tasks? The choice sets the first environment and credit-assignment contract.
2. Must the first distributed release train on TPU while sampling on GPUs, or must training and rollout both run on each target device family?
3. Is cloud sandbox execution acceptable in the eventual product, or must all task execution remain local or self-hosted? What network access and credential policy should agent environments have?
4. Does “inside any agent executor” include unchanged third-party CLI agents behind a model gateway, or can the integration require an instrumented Python agent API?
5. Which trade-off is acceptable for long-running work: an immutable policy per episode, or mixed-policy episodes with recorded token probabilities and correction? Must partial episodes survive trainer and environment preemption?
6. Which retention and safety evaluations must remain above a fixed threshold while task reward improves? What maximum task time, output budget, and judge cost should recipes optimize for?
7. Is exact reproduction of a named proprietary model's recipe an acceptance criterion when its maker has not published the algorithm? Muse Spark 1.3 and Qwen3.8 currently provide incomplete post-training evidence.
