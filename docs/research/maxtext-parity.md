# MaxText configuration parity

Research date: 2026-09-06. Dew source: `65fd2f4`.

This extends [google-jax-stack.md](google-jax-stack.md). Its library verdicts remain the starting point. This note audits configuration and execution at the current Dew seams. Older descriptions of a two-axis Dew mesh, missing MoE, missing scanning and missing async checkpoints no longer describe the code.

## Scope and evidence

The reference is the [MaxText 0.2.4 release](https://pypi.org/project/maxtext/0.2.4/), tag `maxtext-v0.2.4`, commit [`538fe7a3f3376d94cf3f04e77741aa6d7e8efa45`](https://github.com/AI-Hypercomputer/maxtext/tree/538fe7a3f3376d94cf3f04e77741aa6d7e8efa45). The unpacked wheel is `/tmp/mt/maxtext`. Its `configs/base.yml` has 695 top-level keys and 1409 lines. Its SHA-256 is `67fb37c9390dbe1bbe90802d2316619e7ef9f4946ff1cff2bba91d2b6229e38a`. The release-tag copy has the same hash.

The inventory has one row for each top-level key, in source order. A list-valued key such as `logical_axis_rules` remains one knob. The named remat policies and the requested mesh axes have separate matrices after the inventory. A field in the configuration is evidence of a control, not evidence that every model/backend combination supports it. Implementation citations accompany the load-bearing gaps below.

Dew citations point to the source at `65fd2f4`. “Nothing” means no implementation at the matching seam was found. “Unverified” means the surface exists but this research did not establish reference equivalence. Fit entries are recommendations, not approved designs. No model weights, training jobs, cloud resources or GPU benchmarks were used for this note.

Two distinctions affect the ranking. Dew's pipeline computes stages on separate devices, but its persistent parameter and optimizer trees remain replicated across `stage` (`src/dew/training/distributed.py:27-38,205-259`; `src/dew/nn/backbones/causal_transformer.py:592-629,1491-1622`). Dew's sequence attention splits queries but gathers the full K/V sequence (`src/dew/nn/attention.py:395-440`). Neither capability establishes the memory scaling of the corresponding MaxText configuration.

## What dew needs

This order targets training that no longer fits on one accelerator. It does not rank new algorithms by publication date.

1. Decoder activation checkpointing and memory-kind placement. The decoder has no remat policy. Trainer places parameters, optimizer state and EMA in device memory. MaxText selects named residuals and host offload ([nnx_decoders.py:1140-1268](https://github.com/AI-Hypercomputer/maxtext/blob/538fe7a3f3376d94cf3f04e77741aa6d7e8efa45/src/maxtext/layers/nnx_decoders.py#L1140-L1268)); JAX documents the required transfers and `pinned_host` shardings in [memory spaces](https://docs.jax.dev/en/latest/201/memory-spaces.html). Dew evidence: `src/dew/nn/backbones/causal_transformer.py:524-558,821-873`; `src/dew/training/trainer.py:392-408`.
   Fit: Trainer execution/placement capabilities, Linen block remat and Layout memory kinds. Measure residual memory before selecting a policy.

2. Persistent stage-local training state. Dew's GPipe stage view does not reduce stored parameter, moment or EMA residency across `stage`. Its layer patterns must repeat identically across stages. MaxText carries stage/repeat-partitioned weights and a circular schedule ([pipeline.py:589-704,967-1040](https://github.com/AI-Hypercomputer/maxtext/blob/538fe7a3f3376d94cf3f04e77741aa6d7e8efa45/src/maxtext/layers/pipeline.py#L589-L704); [base.yml:309-352][maxtext-base]). Dew evidence: `src/dew/training/distributed.py:27-38,205-259`; `src/dew/nn/backbones/causal_transformer.py:592-629,1491-1622`.
   Fit: MeshSpec/Layout and decoder layer-stack execution. Storage placement must precede bubble optimizations or `num_pipeline_repeats` parity.

3. Physical-topology-aware meshes and activation layouts. Dew has six axes but no ICI/DCN vectors, second FSDP dimension or tensor-sequence phase. MaxText's constructor uses separate slice/device products ([maxtext_utils.py:2154-2276](https://github.com/AI-Hypercomputer/maxtext/blob/538fe7a3f3376d94cf3f04e77741aa6d7e8efa45/src/maxtext/utils/maxtext_utils.py#L2154-L2276)); JAX supplies [hybrid device meshes](https://docs.jax.dev/en/latest/_autosummary/jax.experimental.mesh_utils.create_hybrid_device_mesh.html). Dew evidence: `src/dew/training/distributed.py:75-154,205-259,308-340`.
   Fit: MeshSpec/Layout. Each added axis needs parameter, activation, batch and optimizer consumers.

4. Dropless expert communication remains open for required bf16 workloads. Kernel selection is already reachable through `Mixture.implementation`. The outside-release fp32 increment adds `Mixture.dispatch='exchange'` using public `all_to_all`, while `'global'` remains the default. With S expert shards and L local slots, each round carries S * ceil(L/S) rows; at most S rounds drain every bucket without dropping assignments. A collective maximum chooses the actual round count. Reverse-mode recomputes each round instead of retaining all expert intermediates. Tests compare outputs, input/router-weight/kernel gradients, idle experts, worst-case skew and padded token axes, including actual two-process CPU collectives (`tests/test_moe_exchange.py`).

   Reproduction: `JAX_PLATFORMS=cpu XLA_FLAGS=--xla_force_host_platform_device_count=8 PYTHONPATH=src python tools/moe_exchange_probe.py`, JAX/jaxlib 0.11.1, NumPy 2.5.2 and ml_dtypes 0.6.0, on an i9-12900K. At 256 tokens, width 64, hidden width 128, 8 experts, top-k 2 and expert=4/fsdp=2 with identical input/output placements, forward temporary memory was 854,288 bytes global versus 282,464 exchange; backward was 2,067,216 versus 1,582,600. Outputs matched exactly and maximum gradient difference was 3.50e-10. Ten-call CPU medians were 1.192 versus 0.952 ms forward, 2.954 versus 3.315 ms backward. This reduced the working buffers, not the measured backward time; GPU/TPU throughput is unmeasured.

   The same script isolates the remaining precision blocker with NumPy float64 contractions of explicitly bf16-rounded operands. For identical inputs, unplaced JIT and placed expert=2/fsdp=4 or expert=4/fsdp=2 global gradients match that oracle within 5.96e-8. Eager execution, replicated gradient outputs and expert=8/fsdp=1 instead match the once-bf16-rounded gradient oracle exactly. The two oracles differ by 0.0135841, with 1,021 of 1,024 elements changing. Always accumulating chunk cotangents in either bf16 or fp32 therefore misses an existing global outcome. A candidate fp32 transpose passed two-process bf16 SwiGLU tests but failed the expert-only placement. Separately, global exact-GELU HLO passes an fp32 product to `erfc` while the scan body retains an extra bf16 conversion before `erfc`; a tiny case differed by 0.00390625 in outputs. No CPU-pass-order-specific activation rewrite, layout-dependent gradient cast, fallback or relaxed tolerance was adopted. Public exchange rejects bf16 until this shared precision contract is resolved with a mathematical oracle; the overall exchange gap is not closed.

   The opt-in investigation in `tools/moe_precision_candidate.py` gives global and exchanged execution one shared precision rule. Complete forward contractions accumulate at least in fp32 before their output cast. Derivative contractions use a common work dtype covering the configured operand dtype and both original input/master dtypes, then return cotangents to their original dtype after reduction. Exact GELU and its derivatives evaluate at least in fp32. Custom JVP rules use rounded operand values with straight-through master tangents, supporting JVPs, VJPs and both mixed second-order directions without CPU- or layout-dependent branches. Independent NumPy/SciPy oracles cover these modes, including fp64 retention and 1,024 weighted exact-GELU inputs. Exact 2^-30 cancellation checks cover implicit fp64 promotion, explicit fp64 compute and both mixed orders under bf16 compute; generic fp32 absolute tolerance would miss those regressions. Three Adam steps compare outputs, gradients, parameters and moments for all three activations on expert/fsdp layouts 2/4, 4/2 and 8/1, under random and skewed routing with input scaling and clipping. Two real CPU processes also exercise full expert-block JVPs (exact equality) and all optimizer cases (maximum difference 5.97e-8) at unchanged 3e-5 tolerance. The tool reports unchanged-global, corrected-global and exchange costs separately. This candidate intentionally corrects historical bf16 results; production precision and dispatch defaults remain unchanged pending cutover approval.

   Independent review exposed premature rounding of contracting-width shard partials in the candidate forward and input transpose. Both now accumulate the complete contraction at least in fp32 before their final dtype cast. The expanded 72-case NumPy oracle matrix covers row- and column-sharded kernels, placed and replicated gradients, fp32/fp64 master and input boundaries, and adversarial 1 + 2^-8 + 2^-8 sums. Forward outputs match exactly; maximum kernel-gradient error is 2.39e-7 and input-gradient error 9.54e-7 (bf16 input gradients are exact). This correction remains in the opt-in candidate only.

5. Fused attention for the model shapes Dew currently sends to XLA. Softcaps, sinks and wide heads currently exclude Dew's fused paths. TPU uses the older Pallas flash function.    Fit: attention_impl with explicit backend constraints. No TPU/Hopper speedup was measured here.

6. Bounded-memory context attention. Full-KV all-gather limits the benefit of Dew's sequence axis. MaxText has ring, Ulysses and USP paths, with backend restrictions ([attention_op.py:615-725](https://github.com/AI-Hypercomputer/maxtext/blob/538fe7a3f3376d94cf3f04e77741aa6d7e8efa45/src/maxtext/layers/attention_op.py#L615-L725); [base.yml:1198-1201][maxtext-base]).    Fit: attention_impl and MeshSpec/Layout. Preserve packed-document masks, windows and exact rotary positions. Ulysses/USP in this MaxText release are TPU-specific.

MaxText distinguishes dense warmup and sparse indexer training ([base.yml:430-445][maxtext-base]; [indexer loss implementation](https://github.com/AI-Hypercomputer/maxtext/blob/538fe7a3f3376d94cf3f04e77741aa6d7e8efa45/src/maxtext/layers/attention_mla.py#L1317-L1327) and [training loss](https://github.com/AI-Hypercomputer/maxtext/blob/538fe7a3f3376d94cf3f04e77741aa6d7e8efa45/src/maxtext/trainers/pre_train/train.py#L348-L355)). ### Gaps that do not need a core Dew capability

1. Google-only diagnostic products and traffic-control switches. Vertex TensorBoard, managed ML Diagnostics, Cloud Logging and Linux network throttling are deployment choices ([base.yml:906-913,944-952,1066-1081][maxtext-base]). Dew already accepts a Tracker and pre-backend flags (`src/dew/training/trainer.py:178-218`; `src/dew/training/runtime.py:27-55`).
   Fit: deployment tooling or a Tracker implementation. They do not belong in the training algorithm API.
2. Legacy AQT, internal topology APIs and temporary Transformer Engine workarounds. Dew's quantization seam uses Qwix (`src/dew/training/quantization.py:131-157`); MaxText labels its quantization transition and workaround in [base.yml:149,523-525,1213-1214][maxtext-base].
   Fit: does not fit core parity. Match a required numeric format through Qwix, not an obsolete provider or a private Google API.
3. Token dropping, unscaled FP8 Q/K and guessed logit maxima as default optimizations. These choices alter arithmetic or token coverage ([base.yml:217-224,1192-1194][maxtext-base]). Dew's optimization contract requires retained semantics (`CONTRIBUTING.md:22-30`).
   Fit: optional Objective/quantization experiments after explicit owner approval. They do not close an exact-performance gap.
4. A wholesale NNX rewrite. JAX remat, memory kinds, sharding and Pallas kernels do not require NNX. Dew's pure Linen variables reach one Trainer step (`src/dew/training/trainer.py:224-238,274-349`). The [Flax migration guide](https://flax.readthedocs.io/en/latest/migrating/linen_to_nnx.html) shows the graph/state and initialization changes.
   Fit: retain Linen. Evaluate a specific NNX interop boundary only when an upstream consumer requires it.
5. Pathways live elasticity before a Pathways deployment exists. MaxText explicitly limits this mechanism to Pathways ([base.yml:1403-1409][maxtext-base]). Dew joins multi-controller JAX (`src/dew/training/runtime.py:62-79`).
   Fit: does not fit the current runtime. Portable restart and global data position remain useful without Pathways.

## Open questions for the owner

1. Which topology is the first scale target: TPU generation/slice count, or GPU generation/node count/interconnect? The kernel and mesh priorities depend on it.
2. Must live resource resizing work under portable multi-controller JAX, or is a Pathways-specific execution mode an acceptable deployment target?
3. Should arithmetic-changing modes such as token dropping and unscaled FP8 attention remain outside Dew's supported training recipes, even when MaxText exposes them? They cannot satisfy the current exact-optimization contract.
