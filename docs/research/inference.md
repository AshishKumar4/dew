# Inference and rollout serving

Research checked on 2026-09-06. Dew citations refer to `65fd2f4`. Upstream source links pin commits. Hosted documentation describes the page retrieved on this date. MaxText package observations refer to `maxtext==0.2.4`, unpacked at `/tmp/mt/maxtext`; the linked source snapshot is `c55443590e2925b5da66f82ea7bc9a32a8c662e3`. Their line numbers differ. Package citations below use package-relative paths.

This note records capabilities and fit recommendations. It makes no interface decision. It reports no throughput measurement or end-to-end compatibility result. I read source and documentation without loading model weights or running a serving engine. A kernel or export path in source does not establish model-wide serving parity.

## Dew today

`generate(model, params, prompt, max_new_tokens, *, key, temperature=1.0, top_k=None)` accepts a full Flax variables dictionary and a rectangular token batch. It allocates a new cache, prefills the prompt, samples the first token, and runs the remaining tokens through `lax.scan`. It returns the prompt and generated ids together. The model, length and sampling knobs are JIT-static (`src/dew/sampling/text.py:16-53,77-107`).

The ordinary attention cache contains keys and values of shape `[batch, max_seq_len, kv_heads, head_dim]` and one scalar write index. Decode rejects `sequence > 1`. The attention mixer appends to that cache and constructs a mask over its allocated width (`src/dew/nn/attention.py:262-310`; `src/dew/nn/mixers/attention.py:195-213,269-280`). Its `kv_store` shares a provider layer's K/V with other layers of the same model. It does not share prompt storage between requests (`src/dew/nn/mixers/attention.py:162-171,235-240,279-280`). Dense MLA has a separate compressed-latent cache path (`src/dew/nn/mla.py:1-13`).

`SampledRollout` calls `generate` once per group in a Python list comprehension. Each call batches the prompt rows, repeats prefill, and copies its result to NumPy. Rewards see the entire fixed-width completion. EOS affects the response mask after reward evaluation. The objective then rescores all concatenated sequences (`src/dew/objectives/rl/rollout.py:97-155`). The trainer already accepts a host-side `Rollout` and reshards its returned batch before the compiled update (`src/dew/training/trainer.py:59-68,485-498`).

Gaussian diffusion sampling already separates the `Process`, solver step, guidance wrapper and pipeline. `sample` scans the time intervals and returns one final clean prediction. `CFG` supports an interval. `TextToImage` loads a Dew run and encodes prompts before the sampling JIT (`src/dew/sampling/sample.py:8-35`; `src/dew/sampling/guidance.py:11-43`; `src/dew/sampling/pipelines.py:23-74,87-123`). DiffusionGemma uses a causal prefix cache and a bidirectional token canvas. Its canvas sampler uses a Python denoising loop and a final argmax (`src/dew/diffusion/block.py:100-170`).

`save_hf_layout` writes a container and the supplied config without translating either vocabulary. `save_pretrained_decoder` performs family-specific translation before calling it. That exporter refuses several loaded architectures, including KV-sharing/value-normalized models, non-attention mixers and routed families without an export tensor map. It writes a `tokenizer_name` field when supplied; it does not copy tokenizer assets (`src/dew/interop/safetensors_io.py:85-95`; `src/dew/interop/hf_decoders.py:2068-2125`). A successful load is therefore insufficient evidence for an external rollout path.

## Serving engines

The vLLM PagedAttention paper establishes block-based KV allocation and sharing. Its old kernel-design page now labels itself historical. The current prefix-cache design remains a useful source for block ownership, reference counts and cache identity. The rows below use the paper and current documents together, without assuming that the 2023 CUDA kernel describes every current backend ([paper][V-paper], [historical kernel notice][V-historical], [current prefix cache][V-prefix]).

### JAX and TPU engines

The current vLLM TPU path runs JAX. `tpu-inference` supports native JAX model definitions and PyTorch definitions lowered through Torchax into JAX/XLA. `vllm-tpu` is the installation package for this stack, not another independent engine. Its 0.28.0 package metadata depends on `tpu-inference==0.28.0` ([backend report][T-blog], [quickstart][T-install], [package metadata][T-package]). These facts do not establish a direct adapter for Dew's Linen variables.

JetStream's README announces retirement and migration to `tpu-inference`, with a planned archival date of 2026-02-01. The GitHub API still reported `archived: false` when checked. Its last main commit was from January 2026. Treat it as a reference interface with an announced retirement, not an actively developing dependency ([notice][J-readme], [repository metadata][J-status]).

The JAX kernels above live under `experimental`. The JAX RPA source expects K/V already written to its page array. The TPU backend report describes a separate RPA v3 implementation that fuses cache update with attention. They are different interfaces ([JAX RPA][P-ragged], [RPA v3 report][T-blog]). MaxText also keeps its own non-paged ragged kernel. Its package adapter includes a quantized-input refusal; it does not prove that ragged attention and KV quantization compose (`maxtext==0.2.4: layers/attention_op.py:1589-1622`).

EasyDeL's inspected main commit is dated 2026-04-22. Its source establishes a shipping implementation. This pass did not establish current production deployments or measured parity with vLLM. Tunix's integration provides stronger evidence of an RL user for vLLM TPU and SGLang-JAX ([EasyDeL commit][E-commit], [Tunix source][U-source]).

## Rollout throughput

Research-scale fit depends on measured completion lengths, group count, cache memory and the share of wall time spent generating. Dew already records `train/rollout_seconds` (`src/dew/training/trainer.py:492-496,534-540`). A research-scale crossover cannot be assigned a model-size or device-count threshold from the evidence in this note.

The source shows two correctness gaps before throughput work. `prompt_length` never reaches `generate`, so the attention cache includes left padding as prompt content. EOS changes the loss mask but does not trim the string passed to reward (`src/dew/objectives/rl/rollout.py:100-135`; `src/dew/nn/mixers/attention.py:195-198,275-278`). These are source observations, not reproduced numerical failures.

[INFERENCE] At temperature other than one, Dew's recorded `old_log_probs` do not describe the transformed distribution that drew the tokens. The sampler divides logits by temperature, while the scorer returns untempered negative cross entropy (`src/dew/sampling/text.py:16-25`; `src/dew/objectives/lm/objective.py:345-349`). A designer must specify both the behavior-policy distribution and the training ratio. Replacing generation with a remote endpoint without this distinction would preserve the ambiguity.

At small scale, the in-process route can reuse training variables and avoid an export/refit cycle. It also keeps trainer state and rollout cache in the same accelerator memory budget (`src/dew/objectives/rl/rollout.py:112-117`). At pod scale, an external engine offers request scheduling, separate decode placement and overlap. It adds parameter transfer and policy staleness ([verl workers][L-doc], [Tunix rollout][U-doc], [prime-rl overview][R-overview]). Colocation concerns device ownership; an optimized engine can still run in-process. Tunix demonstrates that distinction.

A live weight update needs more than an HF checkpoint. The adapter must map and reshard tensors, coordinate in-flight requests, commit a weight version, and prevent reuse of K/V from old weights. vLLM's native protocol and prime-rl's version-salted caches document these concerns ([weight transfer][V-sync], [pause semantics][V-sync-blog], [policy cache semantics][R-alg]). GPU NCCL/CUDA IPC support does not establish a JAX-to-TPU transfer path. Tunix is the relevant JAX integration reference. Dew has no such adapter today.

`MultiStepDPM` is not an implementation of DPM-Solver++. It forms derivatives from past epsilon values and advances with powers of the sigma increment. `DPMSolverPP` is the DPM-Solver++ (2M) update in half-log-SNR, one algorithm of the several `DPMSolverMultistepScheduler` names (`src/dew/sampling/solvers.py`; [DPM source][D-dpm]); the other algorithms, orders and stochastic modes of that class remain separate solvers to write.

Dew's `steps` counts grid points, followed by a final clean prediction. Diffusers schedulers own their inference timestep sequences. Numerical comparison must fix the initial noise, model prediction convention, grid, guidance and terminal behavior (`src/dew/sampling/sample.py:19-35`; `src/dew/diffusion/process.py:40-47`; [scheduler overview][D-overview]). The DiffusionGemma canvas is a separate token-sampling process. The Gaussian scheduler matrix does not establish its serving compatibility (`src/dew/diffusion/block.py:149-170`).

GGUF is a container with runtime-specific tensor types and metadata. Weight quantization and KV quantization are separate operations. llama.cpp's guide documents potential accuracy loss from weight quantization; its server exposes separate K/V cache types ([quantization guide][C-quant], [server options][C-server]). Dew's current contribution contract rejects reduced-precision changes presented as transparent optimizations (`CONTRIBUTING.md:30-32`). Any quantized rollout proposal needs a separate, owner-approved numerical contract.

## Inference interface options

`docs/design/api.md:41-48` requires frozen configuration values, PyTrees across JIT, protocols for interchangeable implementations, explicit keys and rejection of unknown fields. Its inference example keeps generation beside the trainer (`docs/design/api.md:266-273`). Section 10 of the post-training design places external serving behind `Rollout` (`docs/design/post-training.md:172-174`). The current trainer call site supports that location; export completeness and live weight sync remain gaps.

A token-level `generate` can continue to accept the model, full variables, token ids and `key`. Ragged prompts need one canonical representation of validity, such as lengths or a mask. A string/chat entry can render with a tokenizer before calling the token-level function. The existing API and HF's tool-aware rendering illustrate those two concerns (`src/dew/sampling/text.py:77-107`; [tool templates][H-tools]).

| What it is | Who ships it (source) | What Dew has today | Gap | Fit |
| --- | --- | --- | --- | --- |
| Generation configuration value | HF `GenerationConfig` and vLLM `SamplingParams` collect request settings ([HF][H-config], [vLLM][V-sampling]). | Separate keyword arguments, `src/dew/sampling/text.py:77-78`. | A serializable, typed `Sampling` contract. | Option A puts distribution and termination fields in one value. Option B gives `Sampling` distribution fields and a separate stopping value. Choose one owner for each field. |
| Sampling content | HF/vLLM expose temperature, probability filters and history penalties ([HF][H-config], [vLLM][V-sampling]). | Temperature/top-k only, `src/dew/sampling/text.py:16-25`. | Ordered transformations and validation. | `Sampling` carries chosen algorithm, temperature, filters and penalty settings. Engine address, mesh and parameter precision belong elsewhere. `key` remains a runtime argument. |
| New-token limit | HF and vLLM express a completion budget ([HF][H-config], [vLLM][V-sampling]). | Required positional `max_new_tokens`, `src/dew/sampling/text.py:77-78`. | Placement relative to a configuration value. | Keep the call argument or move it to the chosen stopping owner. | Server and export lifecycle | vLLM has explicit engine/refit operations; Dew already has a host capability ([protocol][V-sync]; `src/dew/training/trainer.py:59-68`). | `Rollout`, `src/dew/training/trainer.py:59-68`; standalone export, `src/dew/interop/hf_decoders.py:2068-2125`. | Engine construction/use/close, weight mapping and version commit. | Standalone serving beside `Trainer`; a `Rollout` adapter performs network/refit effects. `Objective` continues to consume arrays. |

A streaming implementation could call the same decode step from a host driver, or consume an external engine stream. A batch-only implementation could retain a compiled bounded loop. These are execution choices. They need no separate probability-transform vocabulary. A cache or execution value could configure capacity, shape buckets and placement without changing what `Sampling` means (`docs/design/api.md:43-48`; `src/dew/sampling/text.py:53-74`).

## What dew needs

These are priorities for subsequent design work. Fit lines identify existing seams, not approved interfaces.

1. Correct prompt validity and completion termination. Use prompt lengths during prefill. Return completion lengths. Stop or exclude finished work and trim reward input at EOS. The current omissions are at `src/dew/objectives/rl/rollout.py:100-135` and `src/dew/sampling/text.py:28-48`.
   Fit: sampling owns masks, positions and termination; `Rollout` owns reward text.
2. Explicit likelihood provenance. Preserve the distribution and policy version used to sample each completion. Distinguish raw-model and processed-sampler logprobs before using either in an RL ratio (`src/dew/objectives/lm/objective.py:345-349`; [Tunix output][U-source]; [prime-rl semantics][R-alg]).
   Fit: sampling results and the `Rollout` batch; `Objective` owns the ratio definition.
3. Batched group generation with one prefill per prompt. Reuse immutable prefixes and keep suffix state independent. Measure cache copying separately from physical prefix sharing (`src/dew/objectives/rl/rollout.py:112-118`; [MaxEngine multisampling][M-multi]; [PagedAttention][V-paper]).
   Fit: sampling prefix/decode split used by `SampledRollout`.
4. A typed sampling and stopping contract. Add top-p/min-p, required penalties, stop strings and pure logits processors without duplicate configuration owners. The two value layouts above remain options ([HF config][H-config]; `docs/design/api.md:41-48`).
   Fit: frozen sampling values plus decode-state PyTrees.
5. Decode placement and bounded shape buckets. Make cache capacity, prompt validity, decode sharding and output placement explicit. Profile useful tokens per second, cache memory and compilation frequency before adding paged native execution (`src/dew/sampling/text.py:53-74`; `src/dew/nn/attention.py:276-295`; [HF cache tradeoffs][H-cache]).
   Fit: `MeshSpec`/`Layout`, sampling state and decode-specific `attention_impl` adapters.
6. Complete external model artifacts for selected families. Export correct tensor/config mappings, tokenizer assets and templates. Establish target-engine acceptance per family. Loading coverage currently exceeds export coverage (`src/dew/interop/hf_decoders.py:2034-2125,2280-2302`).
   Fit: the existing `DecoderFamily` registry and interop export functions.
7. External-engine rollouts with live weight synchronization. Implement the selected vLLM GPU or TPU path, including policy versions, request handling during updates and stale-cache invalidation. Test the actual trainer/engine dtype and topology combination ([vLLM protocol][V-sync], [Tunix integration][U-doc]).
   Fit: a `Rollout` capability; transport and refit remain outside `Trainer` and `Objective`.
8. Streaming and tool-aware constrained generation. Preserve tool schemas and message metadata. Return token-level outcomes usable by agent environments. Use the engine's structured-output implementation where possible ([HF tools][H-tools], [vLLM constraints][V-structured]; `src/dew/data/prompts.py:67-90`).
   Fit: host rendering plus the existing rollout capability; a host driver can stream native decode.
9. Selected diffusion scheduler and guidance parity. Prioritize genuine DPM-Solver++ support, exact timestep conventions, guidance rescale and interval semantics. Keep the current finite-difference sampler distinct ([DPM source][D-dpm], [CFG source][D-cfg]; `src/dew/sampling/solvers.py:198-227`).
   Fit: `Process`, `Solver` and the guidance wrapper.
10. Task-level diffusion inference and adapter loading. Add image-to-image, inpainting, encoded prompt inputs and LoRA loading for the model families the owner selects. Each needs a complete task pipeline, not just a sampler ([image guide][D-img], [inpaint guide][D-inpaint], [LoRA loader][D-lora], [prompt inputs][D-prompt]).
    Fit: pipelines and input conditioning beside `Process`; interop owns adapter weights.

## Open questions for the owner

- Which model families and GPU/TPU topologies must the first external rollout path support? That choice determines the export and weight-sync target.
- What useful-completion throughput and interactive latency targets define success at research scale and pod scale? Which prompt/completion length distributions and group counts should those targets use?
- May rollout serving use lossy weight or KV quantization under a separate numerical contract? If so, what quality and likelihood-error bounds are acceptable?
- Must RL remain synchronous with one fixed policy version per completion, or may an agentic rollout span updates? What staleness bound is acceptable?
- Which image-model pipelines need full inference interoperability first? The answer sets the order of scheduler, autoencoder, text-encoder and LoRA mappings.
