# How the frontier and the large open labs train, and what Dew should take from it

Research note, 2026-09-02.

## How this was done, and how to read it

Every claim below comes from a primary source: the lab's own tech report (arXiv PDF), its official GitHub org, its own blog, or the released model's `config.json` and model card, read directly through `huggingface_hub`/`read` on this workstation. Where a fact is not in a primary source I say **not found** rather than guess. Several premises in the assignment were wrong and are corrected inline; the corrections are themselves findings, because they mark where the secondary-reporting layer has drifted from the record. Numbers for 2025-2026 releases were verified against the Hub (existence via `HfApi().list_models`, geometry via `config.json`) before being written down, because models like DeepSeek-V4, Kimi K3, GLM-5.3, Qwen3.8, Gemma 4 and MiniMax-M3 postdate training data.

Scratch artifacts from this survey lived under `/tmp/research/frontier/` (paper text dumps, configs); that tree was wiped mid-survey by an external cause, so per-lab notes are preserved in the session record rather than on disk.

| data pipeline | `dew.data`, grain sources |
| checkpointing | `dew.checkpoints` + `ObjectiveTrainer.save` (orbax step directories, registry push) |

One split is applied throughout the synthesis: what matters on a single 16 GB GPU or one TPU host versus what only matters at thousands of chips. Dew is the former. Google's own reports draw this line sharply, so it is not a convenience split.

## Per-lab notes

### DeepSeek

**Sources.** V2 arXiv 2405.04434; V3 arXiv 2412.19437; V3.1 HF model card (no paper; 2508.17461 is an unrelated astro-ph paper); V3.2 arXiv 2512.02556 plus the V3.2-Exp GitHub PDF; V4 arXiv 2606.19348 ("preview version"); Fire-Flyer SC24 arXiv 2408.14158; `deepseek-ai` GitHub org; configs fetched from HF.

**Corrections.** V2 does not use aux-loss-free balancing - it uses three explicit auxiliary losses (expert α=0.003, device α=0.05, comm α=0.02) plus device-level token dropping; aux-loss-free arrived in V3. The V3 report contains **no** hardware-failure statistics and no "3-layer debugging stack"; the only reliability sentence is "we did not encounter any irrecoverable loss spikes or have to roll back". DeepSeek's real failure statistics exist only in the Fire-Flyer paper, and they describe a different cluster (10,000 PCIe A100s): 12,970 GPU Xid errors in a year (~35.5 events per cluster-day across 10k GPUs, 42.6% NVLink, 33.5% illegal memory access, ~2% memory ECC), with a validator suite run weekly per node that removes faulty nodes from scheduling.

**V3 (arXiv 2412.19437).** 671B/37B, 61 layers, MLA (128 heads, KV compression 512, decoupled RoPE dim 64), first 3 layers dense, 1 shared + 256 routed experts, top-8, vocab 128K. Trained on 2048 H800 under HAI-LLM: 16-way DualPipe PP + 64-way EP over 8 nodes + ZeRO-1 DP, deliberately no TP. FP8 mixed precision, first at this scale: all three GEMMs in FP8 E4M3 with fine-grained scaling (activations 1×128 tiles, weights 128×128 blocks), embedding/head/norms/attention/MoE-gating kept BF16/FP32, master weights FP32. AdamW with the exact WSD-shaped schedule: linear warmup to 2.2e-4 over 2K steps, constant until 10T tokens, cosine to 2.2e-5 over 4.3T, then 2.2e-5 (333B) and 7.3e-6 (167B); batch 3072→15360 sequences. MTP depth 1 with shared embedding/head, loss weight 0.3→0.1, 85-90% second-token acceptance, 1.8× TPS in speculative decoding. Long context: YaRN applied only to the decoupled shared key, s=40, t=0.1·ln(s)+1, two stages of 1000 steps (32K then 128K) at the final pretraining LR. Data: 14.8T tokens, FIM at rate 0.1, document packing without cross-sample masking. Cost: 180K H800-hours per trillion tokens; 2.788M H800-hours total. Checkpointing in the report: none - but the CPU-resident EMA of parameters updated each step is described (§3.2.3), which is a nice vindication of Dew's own EMA seam.

**V3.1 / V3.2.** V3.1 is a card-only release: same architecture, hybrid thinking via template, UE8M0 FP8 scale format on weights and activations. V3.2 adds DeepSeek Sparse Attention: a Lightning indexer `I = Σ_h w_h·ReLU(q_h·k)` (64 heads × 128 dim, ReLU chosen for throughput, FP8-capable) plus top-2048 fine-grained token selection, instantiated on MLA's MQA mode. The adaptation recipe is the interesting part: stage 1 freezes everything but the indexer and trains it for 1000 steps at LR 1e-3 against the L1-normalized head-summed attention distribution under KL; stage 2 enables top-k selection at 7.3e-6 for 20B tokens, with the indexer input **detached** so the two gradient paths stay disjoint. GLM's later comparison: DeepSeek's own adaptation cost 943.7B tokens (V3.1's long-context extension had been scaled up 10×/3.3× to 630B/209B); GLM's DSA warm-up needed 20B.

**V4 (arXiv 2606.19348, 2026-04).** Flash 284B/13B (43 layers), Pro 1.6T/49B (61 layers, 384 experts top-6). Two headline architecture moves: (1) hybrid compressed attention - CSA compresses every m=4 KV entries into one and applies DSA over the compressed set; HCA compresses m'=128 and stays dense; `compress_ratios` interleaves them, with the first two layers pure sliding-window (Flash). (2) mHC, manifold-constrained hyper-connections with 4 residual streams and a doubly-stochastic B_l bounded to spectral norm ≤ 1. KV cache is stored mixed BF16-RoPE/FP8-rest; the lightning indexer runs in FP4. Routing changed to sqrt(softplus) affinity, node limits removed, the first three dense layers replaced by hash-routed MoE. **Muon is now the main optimizer** - update RMS rescaled to 0.18 so AdamW LRs can be reused, two-stage hybrid Newton-Schulz (8 steps of (3.4445, −4.7750, 2.0315) then 2 of (2, −1.5, 0.5) pinning singular values at 1) - with AdamW kept for embedding, prediction head, RMSNorm weights and mHC static biases. And the explicit stability statement: **no QK-Clip, because RMSNorm on queries and KV entries prevents logit explosion at the source**. Two new anti-spike techniques: anticipatory routing (router updated on a lookahead) and a sequence of MoE-outlier controls; spikes were consistently traced to MoE-layer outliers. Determinism and batch invariance are named as debugging infrastructure. Flash trained on 32T tokens, Pro on 33T.

**Open Source Week libraries** (github.com/deepseek-ai, all MIT): FlashMLA (12.9k★, SM90/SM100 CUDA, MQA-mode MLA kernels incl. FP8-KV sparse decode), DeepEP (10.1k★, EP all-to-all dispatch/combine, up to EP2048 in V2, NVIDIA-only), DeepGEMM (FP8/FP4/BF16 GEMMs + fused MoE + the DSA indexer scoring kernels), DualPipe (3k★, the bidirectional schedule plus DualPipeV at PP/2 devices - vendor-neutral, PyTorch 2.0+, the one algorithm here that ports), EPLB (1.4k★, frozen since 2025-03; superseded by LPLB, MIT, LP-based), 3FS (10.2k★, CRAQ distributed FS; checkpoint pattern: async GPU→host then batched parallel writes >10 GiB/s per node, **saves every ~5 minutes, so a failure loses ~5 minutes**), smallpond (5k★, DuckDB wrapper, frozen). Newer: TileKernels (readable TileLang kernels), DeepSpec (speculative decoding research), Engram (sparse embedding lookup). All CUDA/PyTorch; none have a JAX path. HAI-LLM itself has never been open-sourced.

### Moonshot / Kimi

**Sources.** Moonlight arXiv 2502.16982; K2 arXiv 2507.20534; K2.5 arXiv 2602.02276; K3 tech report at github.com/MoonshotAI/Kimi-K3; Kimi Linear arXiv **2510.26692** (the brief's 2508.16328 is a plant-science paper); Mooncake arXiv 2407.00079v4 + FAST '25; checkpoint-engine repo; configs from HF.

**Moonlight / Muon (2502.16982).** 16B-A3B (15.29B/2.24B excluding embeddings), DeepSeek-V3-small shape, 5.7T tokens. Muon: 5 Newton-Schulz iterations, momentum 0.95, NS in BF16, and the scale correction that made Muon industrial - update RMS `0.2·√max(A,B)` so AdamW LRs transfer. Weight decay 0.1 added because vanilla Muon's layer-output RMS grows past BF16 range over long runs; RMSNorm-gamma decay called "crucial". Result: ~52% of AdamW's training FLOPs at compute-optimal performance (~2× compute efficiency). Moonlight also *removes* MTP ("no significant pretraining benefit" at this scale) and modifies the aux-free bias update to subtract the mean sign. Moonlight's claim is about the compute-optimal frontier, not wall-clock MFU; the "1.47× speedup / 48.9% MFU" figures circulating in summaries are **not in any Moonshot primary source**.

**K2 (2507.20534).** 1.04T/32.6B, 384 experts top-8 + 1 shared, one dense layer, MLA. 15.5T tokens: 500-step warmup, 10T at constant 2e-4, 5.5T cosine to 2e-5, weight decay 0.1, **67M-token global batch**. MuonClip = Muon + QK-Clip: per-head (not per-layer) post-update rescaling of Q/K projection weights when a head's max pre-softmax logit exceeds τ=100; for MLA it rescales head-specific q/k by √γ and rotary q by γ, leaving shared rotary k untouched. Rationale: QK-norm is incompatible with MLA because MLA keys are not materialized at inference; softcap acts after logits have grown. In practice 12.7% of heads fired in the first 70k steps, then clipping went inactive. Parallelism: 16-way virtual PP + 16-way EP + ZeRO-1 DP, interleaved 1F1B, ~6 TB of parameter+FP32-gradient state per 256-GPU model-parallel group; runs on any node count divisible by 32. FP8-E4M3 is used for *activation storage* (1×128 tiles) but **not** for compute. Checkpoint engine (for RL): CPU-resident sharded weights, broadcast in <30 s for a full 1T update; the public `checkpoint-engine` repo is MIT, vLLM-specific, benchmarks 14.4-16 s on H20 clusters.

**K2.5 / K2.6 / K2.7-Code.** K2.5 (arXiv 2602.02276) is the multimodal continuation: MoonViT-3D (400M, SigLIP-init) trained 1T tokens, then 15T joint ViT+LLM tokens, then long-context mid-training 32K→262K with a 500B→200B entry; YaRN factor 64 from 4K. Same MuonClip/infra. K2.6/K2.7-Code publish no training reports - cards only, same backbone.

**K3 (June 2026).** 2.78T/104.2B, 93 layers: **69 KDA (Kimi Delta Attention) + 24 Gated MLA** - a 3:1 linear:full hybrid, like Qwen's but with their own KDA mixer. 896 experts **top-16** + 2 shared, latent-MoE width 3584. Per-Head Muon + QK-Clip retained; cosine LR with 1% linear warmup, wd 0.1. Balancing upgraded from fixed-step bias to **Quantile Balancing**: bias computed from the target-load quantile of global score-margin histograms. NoPE; context 8K→64K in pretraining then 256K→1M in cooldown; the linear-attention recurrence replaces RoPE scaling entirely. Pretraining token count, cluster, and LR values: not found. MXFP4/MXFP8 QAT from SFT onward. License: broad use, separate agreement for MaaS above $20M.

**Kimi Linear (2510.26692).** The feasibility study that made K3 possible: 48B-A3B, 27 layers, 3:1 KDA:MLA. KDA refines Gated DeltaNet's scalar decay into a channel-wise diagonal gate, binds the DPLR variables to K (dropping second-level chunk matrices 4→2 and three matmuls, ~100% operator-efficiency gain), uses ShortConv+Swish+L2Norm q/k. 2.3× faster prefill at 512K, 6× faster decode at 1M vs MLA. Fair recipe: MuonClip, WSD, 1.1e-3, 32M-token batch. Compute efficiency vs full MLA: ~1.16× (not 1.47×). MIT weights.

**Mooncake.** Serving infrastructure (KVCache-centric disaggregation; FAST '25 reports 59-498% more requests on real traces). Not training methodology; K2's checkpoint engine uses only its transfer engine.

### Zhipu / GLM

**Sources.** GLM-4.5 arXiv 2508.06471; GLM-5 arXiv 2602.15763; blogs + configs for 4.6/4.7/5.1/5.2/5.3/5.3-Flash; aux-loss-free paper arXiv **2408.15664** (DeepSeek-AI + PKU - not Zhipu, and not 2408.17364); slime at github.com/THUDM/slime.

Muon on everything except embeddings/biases/RMSNorm weights, NS 5, µ 0.95, update RMS 0.2; **cosine, explicitly rejecting WSD** ("WSD models underfit in the stable stage" - worse SimpleQA/MMLU). Batch warmup 16M→64M over 500B tokens. Sigmoid routing + aux-loss-free bias (u=1e-3 for 15T then 0) + sequence-level aux 1e-4, top-8 of 160 + 1 shared, no node limit. **GLM-5 (2602.15763).** 744B/40B (not 44B - Table 10 is authoritative). **slime** (github.com/THUDM/slime, Apache-2.0, 8.36k★, active): Megatron + SGLang + Data Buffer + Ray, colocated or disaggregated. Not liftable into JAX. What transfers as design: Data-Buffer indirection, deterministic train/rollout numerics (logprob delta ~1e-7 as a release criterion), heartbeat health checks, rollout-only/train-only debug replay.

### Qwen

**Sources.** Qwen3 report arXiv 2505.09388; Qwen3-Next blog (2025-09-10); Qwen3.5 blog (2026-02-14); Qwen3.6 blogs; Qwen3.8 blogs; **Qwen3.8-Flash-Next tech report arXiv 2608.30320**; Qwen3-Coder-Next report; GSPO arXiv 2507.18071; SAPO arXiv 2511.20347; global load balancing arXiv 2501.11873; configs from HF (Qwen3.6 is gated, 401).

**Qwen3 (2505.09388).** 36T tokens over three stages: >30T general at 4K, ~5T reasoning at 4K with accelerated LR decay, hundreds of billions at 32K. 119 languages. QK-Norm replaces Qwen2's QKV-bias. The flagship is 235B-A22B with **128 experts top-8 and no shared expert** (94 is the layer count). Optimizer, LR, precision, cluster: all not found - the report only says hyperparameters were fitted per stage from scaling laws. Post-training is the report's other half: 4-stage (long-CoT cold start → GRPO on exactly 3,995 verified pairs, 170 steps → thinking-mode fusion → general RL over >20 tasks), plus strong-to-weak distillation for small models (on-policy KL to teacher logits costs ~1/10 the GPU hours of RL and beat it: AIME'24 74.4 vs 67.6).

**Qwen3-Next-80B-A3B (blog).** 80B/3B, 3:1 GatedDeltaNet:gated-attention hybrid, 512 experts top-10 + 1 shared ("ultra-sparse"), head_dim raised to 256 with partial RoPE on 64 dims, zero-centered RMSNorm (init 0, `x·(1+w)`, weight decay on norm weights because "some layer norm weights become abnormally large"), attention output gating (claimed to eliminate attention sink and massive activations), normalized router init, MTP trained multi-step. 15T tokens (a uniform subset of the 36T) at 9.3% of Qwen3-32B's compute. No "3.6× training speedup" claim exists; the real numbers are compute-cost ratios.

**Qwen3.5 / 3.6.** Native multimodal, same hybrid layout (`full_attention_interval: 4`), MTP on every size down to 0.8B, FP8 pipeline for activations/MoE-routing/GEMM with BF16 sensitive layers (~50% activation memory saved, >10% speedup, "scaling stably to tens of trillions of tokens"), vocab 248K, 201 languages. Qwen3.6's configs are byte-identical to 3.5's - the generation is post-training only. No Qwen3.5 report exists yet (only Qwen3.5-Omni, arXiv 2604.15804).

**Qwen3.8-Flash-Next (arXiv 2608.30320, 2026-08-31).** 125B/6B plus 51B of n-gram embedding parameters held in host memory with async prefetch, plus a 4B MTP module. Four new components: GDN+QSA hybrid (the full-attention layers replaced at continued-pretraining time by Qwen Sparse Attention - an MQA indexer over 4-token pooled keys, partial RoPE, budget 2048 = 512 blocks, 7.6× faster prefill at 1M); **Gated Residual** (4 residual branches, elementwise sigmoid read gate from a d/8 bottleneck, per-branch scalar write gate, no branch mixing - replaces pre-norm); n-gram embeddings (context-keyed lookup, deterministic addressing, one layer only); and a Muon recipe that is the most complete public spec anywhere: NS 8 with Polar-Express coefficients, µ 0.95, γ = 0.2·√max(A,B), Frobenius eps 1e-14, AdamW for embeddings/head/**router** ("Muon exacerbates early-training fluctuations and destabilizes the router")/low-rank GR projections/output gates, Adam-no-wd for the n-gram table, **fused qkv split per head before orthogonalization**, fc1 split into gate/up, grad clip 0.5, **no batch-size warmup** (with Muon, undershooting the optimal batch hurts more than overshooting; batch ramp cost 2.5-3.5e-4 loss and 18.8% more steps), the whole step captured in a CUDA graph because splitting yields ~100 sub-matrices per layer. Stability proven by stress test: at 4× optimal LR, AdamW spikes 183 times per 10k steps and clips continuously; both Muon configs cross the clip threshold zero times; Muon+GR records zero loss spikes. Trained at 1/3 the tokens and ~1/9 the FLOPs of the 397B-A17B flagship for parity on most benchmarks. Parallelism: Megatron TP+DP+ZeRO-1 with **Canzona**, a Muon-aware partitioner that assigns whole parameters by NS-FLOPs and reconstructs matrices via fused all-to-all - the one systems idea here that speaks directly to how a sharded Muon must treat whole matrices.

**Libraries.** FlashQLA (MIT, TileLang GDN kernels, SM90+; the *algorithm* - two-kernel split with CP preprocessing, gate-decay warmup replacing the M-correction matrix - is portable, the kernel is not). GSPO/SAPO: ~20-line RL loss changes; GSPO's sequence-level ratios are tolerant enough of train/infer mismatch that you can optimize on inference-engine likelihoods. Global-batch load-balancing loss: `L = N_E·Σf_i·p_i` with the f-vector synced across parallel groups ("almost free"); balance batch size must reach ~128 sequences to saturate, which for a single-GPU trainer means gradient-accumulation-aware accumulation of f, not just a psum.

A JAX SFT recipe took Sudoku from ~0% to 80% - the cleanest published demonstration of bidirectional attention's planning advantage. Gemini Diffusion itself (I/O 2025) remains a demo with zero training details.

### Meta and OpenAI

**Sources.** Llama 3 arXiv 2407.21783; Llama 4 blog + MODEL_CARD.md + reference code; gpt-oss arXiv 2508.10925 + blog + repo; transformers 5.16.1 `models/gpt_oss/*`, `models/llama4/*`.

**Llama 3 405B.** The most complete public infrastructure write-up. 16,384 H100s (of a 24K-GPU RoCE cluster; 3,072-GPU pods with full bisection, 1:7 oversubscribed aggregation, 16 flows per GPU pair, no DCQCN). 4D parallelism with group order **[TP, CP, PP, DP]** - innermost needs most bandwidth, outermost tolerates latency; FSDP shards optimizer+gradients but does not reshard weights after forward. Three exact configs (Table 4): 8192 GPUs = TP8/CP1/PP16/DP64 at 43% MFU; 16384 = TP8/CP1/PP16/DP128 at 41%; 16384 = TP8/CP16/PP16/DP8 at 128K seq, 38%. Interleaved PP with tunable contiguous micro-batches; one layer removed from first and last stages; no activation checkpointing at 8K. CP is all-gather-based (K/V all-gathered, local Q), chunks assigned i and 2CP−1−i. BF16 with FP32 gradient accumulation and FP32 reduce-scatter. AdamW 8e-5, 8000-step warmup, cosine to 8e-7 over 1.2M steps; batch 4M→8M→16M tokens. Note what is *absent*: no QK-norm, no z-loss, no softcap, no MTP, no gradient-clipping value, no Adam hyperparameters - Meta's stability came from batch ramping and FP32 accumulation alone.

**Llama 4.** No tech report; blog + card + reference code only. Scout 109B/17B (16 experts top-1, MoE every layer, QK-norm after RoPE, scaled RoPE ×16, 10M context) and Maverick 400B/17B (128 experts top-1 every 2nd layer, no QK-norm, 1M). iRoPE: every 4th layer is NoPE with global attention, the rest chunked local (8192) + inference-time attention temperature tuning `log(floor((pos+1)/8192)+1)·0.1+1` applied only on NoPE layers. **FP8 pre-training** (Behemoth: 32K GPUs at 390 TFLOPs/GPU); granularity not found. **MetaP**: per-layer LRs and init scales that "transfer well across batch size, model width, depth, and tokens" - no values published. Codistilled from Behemoth with a dynamic soft/hard target loss. Scout ~40T tokens, Maverick ~22T.

**gpt-oss (2508.10925).** 120b = 116.8B/5.1B active, 36 layers, 128 experts top-4 with softmax over selected logits only, router and attention have biases. **MXFP4 in post-training** (4.25 bits/param: 32 FP4 values + one E8M0 scale byte per 16-byte block): all 36 layers' expert weights quantized - attention, router, embeddings, lm_head, norms, and expert *biases* stay BF16; there is no first/last-layer exclusion (that is Llama 3's FP8 *inference* rule). Per-head learned softmax sinks (one bf16 scalar per head per layer, concatenated as an extra logit column). Optimizer, LR, batch, parallelism, balancing loss: all not found. Apache-2.0 weights and code, but no training code - "released, not trained open". ### MiniMax and Mistral

**Sources.** MiniMax-01 arXiv 2501.08313; M1 arXiv 2506.13585; M2 series arXiv 2605.26494v2 (covers M2/M2.5/M2.7); M3/MSA arXiv 2606.13392; Mixtral arXiv 2401.04088; Magistral arXiv 2506.10910; Mistral 3 blog; Ministral 3 arXiv 2601.08584; configs from HF.

**MiniMax-Text-01 / M1.** 456B/45.9B, 32 experts top-2, 7:1 lightning:softmax hybrid, PostNorm + DeepNorm (α=3.5566) because the hybrid is depth-sensitive, varlen ring attention (softmax) + LASP+ (lightning) for CP, EP fully decoupled from non-MoE parallelism, 1500-2500 H800 dynamically. Trained on ~11.5T tokens with a WSD schedule containing a **manual LR cut** (2e-4 → 1.3e-4 mid-run on anomalous gradient norms → exponential to 3e-5) and a batch ramp 16M→128M derived from a fitted critical-batch-size law. M1 (2506.13585): CISPO - clip the importance ratio instead of masking the token, `sg(clip(r, 1−ε_low, 1+ε_high))·Â·logπ`, because under 16 off-policy updates PPO/GRPO clipping kills exactly the rare reflective tokens ("However", "Wait"); DAPO parity at half the steps. Full RL run on **512 H800 in 3 weeks for ≈$534,700** (not $5,347). The other load-bearing fix: an **FP32 LM head** - train/infer probability correlation went from ~0.9 to ~0.99 from that one change, and reward would not grow without it. Repetition truncation (3000 consecutive tokens at p>0.99) as a rollout guard.

**M2 series (2605.26494).** 229.9B/9.8B, 256 experts top-8, sigmoid gating + learnable routing bias, aux loss reduced to 1e-3. The post-mortem on attention is the most valuable negative result in this survey: MiniMax ran lightning attention at 456B and **walked back to full attention on all 62 layers**, after SWA/hybrid experiments spanning "hundreds of billions to trillions of tokens" showed RULER-128K CWE 90.0→72.0 and MTOB e-k ChrF 44.8→27.2 while MMLU/MATH stayed flat - the damage is invisible on the usual benchmarks. MTP: 1 module pretraining, **expanded to 3 by copying main-model weights** in the decay phase, frozen trunk until head loss stabilizes, then joint; MTP co-trained during RL with a top-K KL to keep acceptance up. Forge RL: windowed-FIFO scheduling (W=0.3N), prefix-tree merging of shared rollout prefixes (exact, up to 40×). 29.2T tokens (19.9T constant + 9.3T decay). License drift is real: M2 MIT → M2.1/M2.5 modified-MIT → **M2.7 non-commercial** → M3 community license with a $20M clause.

**M3 / MSA (2606.13392).** ~428B/~23B, 1M context. MiniMax Sparse Attention: one index query head per GQA group + a single shared index key head, block scores = max over visible tokens, top-16 blocks of 128 tokens (2048 attended tokens per query regardless of length), local block forced in. Selector trained with a KL loss against the probability-averaged main-branch distribution with **stop-gradient on the index inputs** - the auxiliary loss touches only the two index projections - plus a dense warm-up phase. 28.4× per-token attention FLOP reduction at 1M; 14.2× prefill / 7.6× decode on H800. Kernels MIT but SM100-only.

**Mixtral / Magistral / current Mistral.** Mixtral 2401.04088 contains **zero** training text: no optimizer, no LR, no token count, no hardware, no balancing loss - 47B/13B, softmax top-2 of 8, routing tracks syntax not domain, strong temporal locality (useful for EP caching). Magistral (2506.10910): GRPO with five named modifications (no KL penalty, token-count loss normalization, minibatch advantage normalization, clip-higher ε_high=0.3, non-diverse-group filtering), fully asynchronous RL where weights broadcast GPU→GPU in <5 s and in-flight sequences keep their KV cache. Entropy bonus and KL-as-entropy-control both failed; tuning ε_high worked. Text-only RL improved vision benchmarks (MMMU +5%). Mistral Large 3: 675B/41B MoE (DeepSeek-V3-shaped MLA), from scratch on **3000 H200s**, Apache-2.0, EAGLE drafter rather than MTP. Ministral 3 (2601.08584) is Mistral's one full modern recipe: cascade distillation (prune → forward-KL distill → repeat) at 1-3T tokens per model, with the teacher-choice findings (stronger teacher is worse for pretraining distillation; post-trained teacher beats pretrained; preference-tuned teacher beats SFT-only).

### NVIDIA hybrids and diffusion language models

**Sources.** Nemotron-H arXiv 2504.03624 (not 03622); Nemotron 3 Ultra arXiv 2606.15007; SDLLM arXiv 2602.15014 + four HF repos; LLaDA arXiv 2502.09992; LLaDA-1.5 arXiv 2505.19223; LLaDA-MoE arXiv 2509.24389; LLaDA2.0 arXiv 2512.15745; Dream arXiv 2508.15487; Mercury arXiv 2506.17298; hackable_diffusion repo; DiffusionGemma (above).

**Nemotron-H (2504.03624).** Dense hybrids, ~8% attention layers (8B: 4/52; 56B: 10/118), **no position embeddings at all** - Mamba supplies position. **Nemotron 3 Ultra (2606.15007).** The most detailed public account of MoE-hybrid divergence. 550B/55B, Mamba-attention hybrid + LatentMoE (512 experts top-22 + shared), 2 shared-weight MTP layers (λ=0.1), **NVFP4 pretraining** (E2M1, 2-D block weights, random Hadamard into wgrad, stochastic rounding; final 15% of layers + Mamba out/latent projections + QKV + MTP + embeddings in high precision; branched BF16 ablations within 0.28% train-loss gap). Two divergences documented: one at 8T traced to FP32→BF16 reduction of the output layer, which erased the MTP blocks' wgrad contribution (MTP loss is scaled 0.05/block); one at 16T undetermined, mitigated by starting LR anneal early. Monitoring advice worth adopting: MaxVio (max expert load / mean; ceiling E/k = 23.27) and residual-norm imbalance as a divergence precursor. Systems: pin EP groups inside one NVLink domain (+20% throughput).

**Diffusion LMs - the mechanism set.** LLaDA 8B (2502.09992): dense 8B, trained **from scratch** on 2.3T tokens, vanilla MHA deliberately (no KV cache anyway), masked CE reweighted by 1/t (proven NLL upper bound), time t not fed to the network (data-prediction is time-invariant for masked diffusion), 1% random-length sequences, AdamW + WSD (4e-4 constant → 1e-4 → 1e-5), low-confidence remasking beats random. Dream 7B (2508.15487): Qwen2.5-7B initialized, **Shift Operation** (keep predicting position i+1 from hidden i, preserving the AR checkpoint's learned positional relationship), CART per-token loss weighting (a mixture of geometrics over distance to clean context - LLaDA2.0 tried it and did not adopt it), 580B tokens of purely open data (Dolma v1.7, OpenCoder, DCLM), beats LLaDA with 1/4 the data; the critical hyperparameter is the LR (too high destroys the AR prior, too low never learns diffusion). LLaDA-1.5: VRPO (DPO with ELBOs; optimal allocation puts the whole MC budget on timesteps, plus antithetic sampling between policy and reference). LLaDA2.0 (2512.15745): the AR→diffusion **conversion** recipe - treat AR as block size 1, warm up block size 1→4→32→…→4096 (now a full MDLM), train large-scale there, then decay block size back down to 32 to regain KV-cache reuse; the numerical fix is Gaussian noise on masked-token embeddings (whose weights decayed to zero during AR training); complementary masking in post-training (both x_t and its complement in one batch) works below 100B tokens only. Mercury (2506.17298): commercial, ~1000+ tok/s on H100, extends SEDD; almost no training detail published. NVIDIA SDLLM (2602.15014): AR/MDLM/Duo/EsoLM at 1.7B on 2.1T tokens, 64 H100 each; the headline scientific result is that the low-variance MDLM objective (replace the diverging α′/(1−α) weight with −1 during training) saves ~12% FLOPs and shifts compute-optimal points to smaller models, and that Duo (uniform-state) **beats AR on GSM8K** (65.8 vs 62.9) despite worse perplexity. SDLLM code is CC BY-NC 4.0 - reference semantics only, do not vendor. The permissive reference stack is **hackable_diffusion** (google/, Apache-2.0): a pure-JAX/Flax/optax toolbox whose `CorruptionProcess` protocol, `CategoricalProcess` (absorbing-mask and uniform-state as special cases), five discrete schedules, `compute_discrete_diffusion_loss` with `use_mask` + `weight_fn` (MD4Loss = LLaDA's 1/t; NoWeightDiscreteLoss = SDLLM's objective), stratified time samplers, and a sampler zoo with pluggable routing/remasking is exactly the objective/corruption/sampling layer Dew lacks - and it is the officially linked fine-tuning path for DiffusionGemma.

## What Dew should take from this

Ordered by evidence of impact: how many independent labs, on their own numbers, show the practice paying off, at what scale it was shown, and what it costs Dew to have it. Items within a tier are roughly interchangeable in priority. "Single-GPU" marks what matters at Dew's scale; everything unmarked in the top tiers also matters there.

### Tier 1 - multiple independent labs, quantified wins, cheap in Dew

1. **Muon with the production recipe, as a second entry in `OPTIMIZER_MAP`.** [borrow: reimplement the idea - `optax.contrib.muon` exists but lacks the production parameter split] Four labs now ship it as the main optimizer: Moonlight (~52% of AdamW FLOPs at compute-optimal, fitted curves), Kimi K2/K3 (MuonClip, zero loss spikes at 1T scale), GLM-4.5/5 (Muon Split, cosine, tolerates larger batches), DeepSeek V4 (update-RMS 0.18 so AdamW LRs transfer), Qwen3.8-Flash-Next (the fullest spec: NS 8, Polar-Express coefficients, µ 0.95, γ=0.2·√max(A,B), Frobenius eps 1e-14, clip 0.5, no batch warmup - and the 4×-LR stress test where AdamW spiked 183 times per 10k steps and Muon zero). The non-negotiable details, now cross-confirmed by three labs: **AdamW (or Adam) stays on embeddings, the LM head, the router, norms/biases, and elongated low-rank projections**; **fused qkv must be split per head before Newton-Schulz** (Jordan's original finding, GLM's Muon Split for MLA, Kimi K3's Per-Head Muon, Qwen's per-head split - four independent convergences); weight decay 0.1 on Muon params; update-RMS rescale 0.2 (0.18 in V4) so existing LR intuition transfers. Single-GPU: yes - this is a per-parameter-group optax chain, and `jax.jit` gives for free the CUDA-graph-style fusion Qwen had to build by hand. Seam: `dew.training.optim`, a `MuonConfig` in `OptimConfig` with the parameter-group labeling done by tree-path inspection.
2. **Zero-centered RMSNorm with weight decay on the scale, as the default norm.** [borrow] Qwen3-Next introduced it because "some layer norm weights become abnormally large" under QK-Norm; it is now on every Qwen model through 3.8 across three generations, MiniMax M3 (`use_gemma_norm: true`), and it is literally Gemma's `(1+w)` scale, which Dew's `RMSNorm(scale_offset=...)` already implements. The one addition the frontier makes that Dew lacks: **apply weight decay to the norm scale** - Moonlight calls RMSNorm-gamma decay "crucial for stability". Seam: `CausalTransformer.norm_eps`/`scale_offset` plus a decay-exclusion rule in the optimizer tree split.
3. **Aux-loss-free MoE balancing, when Dew grows an MoE.** [borrow] The bias-update rule is 10 lines and three labs converged on it independently (DeepSeek invented it, arXiv 2408.15664; GLM and Kimi adopted; Qwen went the other way and keeps a global-batch aux loss at 1e-3 - both work, the bias version needs no loss term). Exact rule: per-expert fp32 bias, added **only for top-k selection**, gating value from the raw affinity; after each step `b_i += u·sign(c_i − c̄)` with u=1e-3, frozen to 0 late in training; a sequence-level aux at 1e-4 as a guardrail. Keep router logits and the bias in fp32 (GLM ships `moe_router_dtype: float32` as a config field - a one-line dtype decision they treat as load-bearing). Kimi K3's upgrade path (quantile-based bias from global score-margin histograms) matters only at hundreds of experts. Seam: the future MoE module in `CausalTransformer`'s MLP slot, with the bias in `TrainState` (never in the optimizer's grad path) and a `psum` of expert counts over the data axis.
4. **Stability at the source instead of after the fact.** [borrow] The 2025→2026 trajectory is unanimous: QK-norm or norm-on-queries/KV *instead of* softcapping logits after they grow (Qwen3, Gemma, MiniMax, Llama 4 Scout); QK-Clip only when the architecture makes QK-norm impossible (Kimi's MLA constraint - and DeepSeek V4 explicitly dropped QK-Clip once RMSNorm-on-queries became possible, GLM-5 dropped all clipping with Muon Split); SwiGLU clamping (gpt-oss ±7, DeepSeek V4 ±10, Kimi K3's SiTU-GLU β1=4/β2=25) as the cheap belt-and-braces. Dew already has `qk_norm` and `final_logit_softcap`; the two missing pieces are the **attention output gate** (Qwen: widens q_proj to 2·H·d, `out·sigmoid(gate)` before o_proj; claimed to eliminate attention sinks and massive activations, and it is what lets Qwen store the residual stream in FP8) and **weight decay on norm weights** (item 2). Also adopt Qwen's **stress-test protocol** as a test, not a feature: hold LR at 2×/4× optimal, count spikes against a 201-step rolling median; it is the only published way to compare optimizers for stability at small scale. Seam: `CausalTransformer` flags + a test in `tests/`.
5. **Document packing and cross-document masking as data-pipeline semantics.** [borrow] Three labs converge: DeepSeek V3 packs documents *without* cross-sample masking; Llama 3 found cross-document masking has "limited impact in standard pre-training, but important in continued pre-training on very long sequences"; LLaDA2.0 calls block-wise masking "crucial" for bidirectional denoising; Qwen's Coder-Next report has the numbers (BFP beats padding with 22% fewer tokens; fragmentation steadily hurts; `drop` beats `split` and `slide` for over-length docs, but they ship `split`). Best-fit-packing with attention-mask-per-document is a grain-side transformation, not a trainer change. Seam: `dew.data` packing stage + mask plumbing into the objective.

### Tier 2 - single-lab or smaller-scale evidence, but cheap and directly in Dew's seams

6. **MTP as an auxiliary objective at depth 1.** [borrow - conditional on the LM objective mattering to Dew] DeepSeek V3 (λ 0.3→0.1, 85-90% acceptance, 1.8× TPS), GLM (trained as 3 parameter-shared steps at the cost of 1 module), Qwen (on every model down to 0.8B, multi-step training to keep train/infer consistent, claimed to improve the backbone itself), MiniMax M2 (expand 1→3 by copy-initializing from the main model, freeze, then joint-train), Nemotron 3 (2 shared-weight MTP layers; λ=0.1). Moonlight is the dissent: no benefit at 16B-A3B. One extra transformer block with shared embedding and head, an extra CE term shifted by one position - this fits the `mixer`/block structure cleanly. If added, port MiniMax's copy-init expansion trick rather than training K>1 from scratch. Seam: an auxiliary head in the LM objective; loss weight schedule in `OptimConfig`.
7. **The discrete-diffusion objective as configuration, via the hackable_diffusion seam.** [adopt: depend on it] Dew has a diffusion objective already; what it lacks is the discrete/text side, and google/hackable_diffusion (Apache-2.0, pure JAX/Flax/optax, the official DiffusionGemma fine-tuning path) supplies exactly the layer: `CorruptionProcess` protocol, `CategoricalProcess` covering absorbing-mask and uniform-state, schedules, `compute_discrete_diffusion_loss` with `use_mask`/`weight_fn`, time samplers, sampler zoo with pluggable routing strategies. With it, LLaDA (MD4Loss = 1/t weight), SDLLM's low-variance objective, and DiffusionGemma's sampler become configuration. Two facts to carry in from the papers: masked diffusion does not need time as a network input (time-invariant data prediction), and Dream's Shift Operation is how you keep an AR checkpoint's positional knowledge through conversion. Do **not** vendor SDLLM code (CC BY-NC 4.0). Seam: a discrete objective in `dew.objectives` composed on hackable_diffusion primitives.
8. **Two-stage long-context extension, and staged RoPE-base bumps instead of interpolation magic.** [borrow] The pattern is universal: pretrain short, extend late at the final LR with long data (DeepSeek's two 1000-step YaRN stages; Gemma 3's 32K→128K at factor 8; Llama 3's six 800B-token stages gated on recovered short-context + perfect NIAH; Qwen3's RoPE-base ×100 via ABF then YaRN+DCA at inference). GLM's version is the cheapest documented: raise θ 1e4→1e6→8e6 with data staging and no rope_scaling at all. Dew's `rope_theta` already parameterizes this; what is missing is the *schedule* concept (a mid-training stage list) and YaRN-on-the-decoupled-key if MLA ever lands. Single-GPU: the extension stages themselves yes; CP at 1M tokens no. Seam: `CausalTransformer.rope_theta` + a staged-train concept in the recipe/config layer.
9. **5:1 local:global attention with a 1024 window as the default `layer_types` pattern, plus the Gemma-4 inference-side KV tricks.** [borrow] Gemma 3's ablation: perplexity-neutral, inference memory overhead 60%→<15% at 32K. Gemma 4 adds three training-free wins on top: p-RoPE (rotate only 25% of head dims on global layers), k=v on global layers, and KV-sharing of the last N layers (−37.5% global KV). All are ~20-line changes in Dew's `CausalTransformer`, which already has `layer_types` and `sliding_window`. Two cautions from the labs' own negative results: fixed 1:1 SWA interleaving is catastrophic without retraining (GLM: RULER 128K 75.3→6.5 zero-shot) - never ship uniform alternation as a default; and MiniMax's full post-mortem says retrieval/induction heads fix early in pretraining and continued training cannot move them, so window patterns belong in the initial architecture, not in a retrofit. gpt-oss's 1:1 with window 128 is the counterexample that works - but with a much smaller window and YaRN'd dense layers doing the long-range work.
10. **WSD-shaped schedules as a first-class alternative to cosine.** [borrow] WSD is now the majority position for new pretraining runs: DeepSeek V3's exact constant→cosine→two-constants shape, LLaDA, Dream, MiniMax (with a manual cut), Nemotron 3 (minus-sqrt decay), Kimi Linear. The counter-evidence is GLM's: WSD "underfits in the stable stage" on SimpleQA/MMLU, so they use cosine. And Qwen's finding that **batch-size warmup is net-negative under Muon** (2.5-3.5e-4 loss cost, 18.8% more steps) means Dew should treat batch ramps as opt-in, not default. Seam: `OptimConfig.learning_rate_schedule` grows a `wsd` literal alongside `cosine`; a batch-schedule field that defaults to constant.

### Tier 3 - real but with a scale or scope qualifier

11. **FP8 with blockwise scaling.** [later - trigger: multi-GPU runs or a model that overflows 16 GB in BF16] DeepSeek V3's recipe (E4M3 everywhere, activations 1×128 tiles, weights 128×128 blocks, norms/attention/gating in BF16/FP32, master weights FP32) is now the open-lab standard; Qwen3.5 runs a native FP8 pipeline to tens of trillions of tokens; Kimi uses FP8 for activation storage only; MiniMax ships FP8 release checkpoints. NVIDIA's Nemotron-H caution applies: FP8 recipes had to be validated at ≥8B/≥1T tokens - smaller-scale validation did not generalize. On a single 16 GB GPU, the win is memory, not speed (no Hopper-specific tensor-core paths from JAX on this workstation), and Dew already has a precision policy module. When it comes: keep the first/last few layers and all norms in BF16 (every lab does), and use UE8M0 scale format (V3.1, V3.2, V4) if targeting microscaling interop.
12. **Sparse attention by retrofit, not by redesign.** [later - trigger: Dew trains past ~64K context] The converged recipe across DeepSeek V3.2, GLM-5, MiniMax M3 and Qwen3.8-Flash-Next: a small indexer (MQA, few heads, ReLU or max-pooled block scores), top-k token or block selection, trained with a KL loss against the main attention distribution, **with the indexer input detached so its gradient never touches the backbone**, after a dense warm-up phase, with the local block always included. Costs: DeepSeek's own adaptation was 943.7B tokens; GLM's redesign got it to 20B; MSA-CPT needed 400B; Qwen replaces the full-attention layers only at continued-pretraining time. The DSA acceptance story (parity with dense attention, 1.5-2× cheaper long-sequence compute, MSA 28.4× FLOP reduction at 1M) is the strongest architecture-level argument in the survey, and the indexer recipe is the portable part. Seam: a new mixer type in `layer_types` plus a two-phase training entry point.
13. **Linear-attention hybrids: adopt the 3:1 ratio vocabulary, not the mixer.** [later - trigger: a decode-throughput-bound use case] The evidence is genuinely two-sided, and the labs that ran it at scale say so: Kimi Linear (2.3-6× speedups, ~1.16× compute efficiency) vs MiniMax M2 (walked back to full attention; damage invisible on standard benchmarks, visible on retrieval/translation; "linear attention is memory-bound even in training... prefix caching and speculative decoding are unsolved"). Qwen's 3:1 GDN:attention is now three generations old and was validated head-to-head (GDN-hybrid 53.81 vs SWA-hybrid 51.15 vs full 49.87 on their 25B ablation). If Dew ever adds a linear mixer, the `mixer` slot is the seam, Kimi's KDA formulation is the reference, FlashQLA's gate-decay-warmup trick is the kernel-side idea worth stealing, and `mamba_ssm_dtype: float32` (Qwen) and `mamba out-projs in high precision` (NVIDIA) are the precision cautions.
14. **Checkpointing and fault tolerance: the cheap half.** [borrow for the parts that fit] At thousands of chips: Meta's numbers (419 unexpected interruptions in 54 days, ~1 per 3.1 h, 3 manual interventions, >90% effective time), Google's elasticity (tens of seconds vs 10+ minutes, ~97% throughput during recovery, 0.25% of steps replayed with 6% genuine SDC), DeepSeek/3FS (async GPU→host then batched writes, save every ~5 min so a failure costs ~5 min), NVIDIA (NVRx async checkpoints; DGX Cloud resilience attributed failures and tripled MTBF). What transfers to one GPU or one TPU host: **deterministic replay + per-device checksums for SDC detection** (Google's cheap half - catches silent corruption in minutes), and **keep the last-N-checkpoint window with periodic validation before pruning** (DeepSeek's validator suite is the cluster version). Dew's orbax manager already keeps `max_checkpoints_to_keep`; the missing piece is a step-level checksum/validation hook. The async-write pattern (host-staging before the registry push) is already present in `ObjectiveTrainer.save`.
15. **RL loss shapes, if Dew ever grows an RL loop.** [later] The portable, evidence-backed set: CISPO (`sg(clip(ratio))·Â·logπ`, in verl, ~10 lines), GSPO's sequence-level ratios (tolerant of train/infer numerical mismatch - lets you optimize on inference-engine likelihoods), Magistral's no-KL + clip-higher tuning + non-diverse-group filtering (entropy bonuses and KL-as-entropy-control both failed), MiniMax's FP32 LM head and repetition truncation (0.9→0.99 probability correlation from one dtype change), GLM's determinism requirement (non-deterministic top-k destroyed RL in a few steps; train/rollout logprob agreement at 1e-7 as a release criterion). If that day comes, the determinism requirement belongs in the test suite from the start.

### What not to take

- **Any DeepSeek/Qwen/MiniMax/NVIDIA kernel or comms library as a dependency.** All are CUDA/SM90/SM100 behind PyTorch bindings; none has a JAX path; DeepEP is multi-node by definition; MSA kernels are SM100-only; FlashKDA is CUTLASS. Their value to Dew is as readable algorithm specs (DualPipeV's schedule, EPLB's placement heuristic, MSA's exp-free top-k and KV-outer iteration, FlashQLA's two-kernel split).
- **Tensor or pipeline parallelism.** Google trains up to 12,288 chips with data × seq × replica + ZeRO-3 and no TP/PP/EP; DeepSeek drops TP on the same reasoning (few activated params + selective recompute); Qwen's Canzona exists only because Megatron sharding fights Muon. Dew's two-axis `(data, fsdp)` mesh is the same shape Google uses minus the sequence axis. The one defensible future axis is `seq` for long-context single-host runs; TP/PP are not defensible on any lab's evidence.
- **Lightning/linear attention as a default mixer** (MiniMax's own post-mortem), **fixed 1:1 SWA interleaving** (GLM's ablation), **partial-credit code rewards in RL** (Magistral: faster, 3× less discarded data, 2% lower final LiveCodeBench), **entropy bonuses** (Magistral again), and **vendoring non-permissively-licensed code** (SDLLM is CC BY-NC; Nemotron-H weights are research-only; note the license drift across MiniMax and Qwen "Community" releases before depending on any 2026 checkpoint).
- **Nothing from Gemini.** Google's frontier models publish no optimizer, LR, precision, or token count. The only transferable Gemini content is the fault-tolerance engineering in the 2.5 report, already covered above.

### Where the record is silent

The practices above rest on what the labs published. Still not found anywhere: Google's optimizer/LR/precision/token counts (all Gemma and Gemini); Qwen3's optimizer and cluster; GLM's cluster size for any model; gpt-oss's optimizer/LR/batch; MiniMax M2's pretraining infra; Llama 4's parallelism and MetaP values; Mercury's nearly everything. Any Dew default sourced from these families (for example a "Gemma-like" LR) has to come from MaxText configs, not from a report.
