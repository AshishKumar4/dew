# Behavioral qualification in Dew

Design record. Tests run real use cases through public interfaces. Kernel math is qualified at representative shapes against float64 truth; other behavior is exercised through end-to-end scenarios. The [roadmap](../roadmap.md#ci-and-tooling) holds coverage gaps and qualification work.

## Scenarios

| Scenario | Flow |
|---|---|
| Dense language-model pretraining | Build a decoder, train, save, resume, evaluate, export, reload and generate. |
| Pretrained fine-tuning | Load a published decoder, train full weights or LoRA, then export and reload both forms. |
| Structured prediction | Train and serve a decision task (dew.decision) |
| Decision ablation workflow | Train a decision task of many options through `dew train` in each cell of a pairwise set over head (joint, question, letters), context, consistency and bound (an examples budget, a share of one), and hold each cell to the conservation contract (`tests/test_decision_workflow.py`). |
| Diffusion training | Train an image or video model, checkpoint, resume, sample and export. |
| Published diffusion pipelines | Load a text-to-image pipeline and sample with its processor, guidance and solver settings. |
| Distributed training | Train dense FSDP and expert-sharded MoE models on real meshes. |
| Online post-training | Collect rollouts, score them, update a policy, save and resume; include language and diffusion RL. |
| Diffusion language models | Train and sample masked and block-diffusion LMs on the shared LM data path. |
| Generation and serving | Evaluate and serve an LM: batch generation, paged cache, speculative decoding, quantized serving |
| Quantized interchange | Load quantized checkpoints (ModelOpt, CT, GGUF) and train or serve them |
| Representation learning | Train a JEPA encoder and evaluate its representations. |
| Hybrid and state-space models | Train and decode GDN, KDA and Mamba through their shared components. |

Each scenario checks every contract its flow touches:

- loss decreases, and the gradient is finite;
- resume equals the uninterrupted run;
- packed rows equal their documents run separately;
- right-padded equals unpadded on the real tokens;
- sharded equals unsharded (on the device mesh of scenario 6 and on CPU multi-device);
- export then reload is identical;
- loaded checkpoints match their reference (HF transformers, diffusers) within the float64 gate.
- a repeated or resumed run reuses its compiled programs: a fresh process hits the persistent cache with an identical program fingerprint (training, evaluation, sampling);
- conservation: a bound in examples counts source examples, whatever rows a layout makes of each; `data/rows` counts the source examples whose rows were delivered, each once, an example refused by any step carried as refused rather than kept (`REFUSED`); where a layout refuses whole examples before it expands them (a decision layout's fit), `data/rejected` counts those examples too, so a run that reads its data whole counts every example written as trained or refused; a step after the expansion counts the rows or windows it rejects in its own unit; and the saved task holds every axis the run sets.

An exact cache's decode agrees with full forward under the numerical rule below. A cache explicitly defined as approximate is compared with the reference implementation's own decode under that same cache. Approximate and exact cache claims remain distinct.

Every Pallas or FFI kernel runs per shard through `tests/sharded.py::assert_runs_per_shard`, with the layer's mesh axes and no unintended collectives. The same flow checks its numerical result against the unsharded reference; compilation alone does not prove shard placement or communication behavior.

## Settings and devices

Each scenario runs a small covering set over the settings axes, chosen pairwise, so every pair of settings meets once:

- precision: fp32, bf16, fp8 where supported;
- rows: padded, packed;
- memory: no remat, the planner's rung;
- devices: 1, 2 (CPU multi-device), the GPU mesh;
- quantization: none, QAT, PTQ (scenarios 2, 9, 10);
- data read: memory, indexed, streamed;
- decision runs: head, context, consistency, and bound kind (examples, a share of them).

Implementations come from their registries. A new implementation cannot opt out by being absent from a hand-kept test list.

**CPU tier (every CI run):** real architectures from their real configs, scaled down (layers, width), plus small real checkpoints that fit (for example SmolLM2-135M). Each scenario takes minutes. Multiprocess and multihost behavior uses real processes, readers and meshes. A single-process mesh simulation is useful evidence for that simulation only. The GPU mesh axis (`tests/test_gpu_mesh.py`, and the mesh-marked `gpu` cells of `tests/test_attention_route.py` and `tests/test_kernel_spills.py`) runs on no fleet of Dew's, whose GPUs are single (owner, 2026-10-30, ledger 2221): NCCL collectives, sharded cuDNN attention and a mesh's FFI calls are unqualified by Dew's CI, and a CPU multi-device mesh qualifies the sharding logic alone.

## GPU landing

A GPU-touching change lands by its row:

| Destination | Change | Qualification timing |
|---|---|---|
| `base/kernels` | Kernel and template pieces | CI runs after each push: interpret-mode check 1 for every mainloop, stability, deviceless compilation and resource checks. |
| `main`, from `base/kernels` | Composed kernel base | CPU CI precedes publish. Train review does not block a green publish. GPU correctness and the no-regression window follow immediately on main. Native runs cover A100 and H100, then A10, L4 and TPU v5e. |
| `main` | Hopper-only path | The native H100 run follows publish. |
| `main` | Other changes reaching GPU-specific behavior | The native tier follows publish on the affected target types. |

CONTRIBUTING.md defines the optimization measures. Bit-identical repeats are a separate contract with two parts. In deterministic mode (`--xla_gpu_deterministic_ops`, `dew._devices.deterministic_ops_requested`), one mainloop with one schedule, run twice on the same inputs, returns the same bits. And exact state round-trips to the bit: a checkpoint restored, a cache read back, a value serialized and read. A default that reduces with atomics, the fastest form where that is faster ([kernel templates](kernel-templates.md#8-determinism-d-and-the-backward)), promises no bitwise repeat, and no test holds it to one; its accuracy is the gate's. The deterministic-mode repeat compares no two implementations and decides no landing of a speed or accuracy change; a mainloop that breaks it is a defect fixed like any other. Exact state's round trips are tests like any other, held bit for bit, a red one red.

Check 1 runs each block's first draw again and requires the same inputs bit for bit (`_of_its_seed`: a draw is seeded host code), and runs its arms again on them and requires the same outputs (`_of_its_inputs`) only where a repeat is promised: on a CPU, or in deterministic mode (`dew._devices.deterministic_ops_requested`). A GPU default that reduces with atomics is never held to a repeat there, and neither is an arm declared to vary from run to run on a GPU (`run_to_run`, with its reason: an accumulation in arrival order a deterministic form would slow 2-2.7 times, row 4448), whose every draw is judged by its one run as every arm's is; the CPU lane holds every arm to it (ledgers 2641, 2842).

The native tier is the suite on a type's own backend: on a GPU (`JAX_PLATFORMS=cuda`) the `gpu`-marked tests, its behavioural flows (`tests/test_gpu_*.py`, each a list of cells a kernel's or a model's property runs natively in: the owner's rule of no unit tests on a GPU), and on a TPU (`JAX_PLATFORMS=tpu`) the `tpu`- and `kernel`-marked tests, each `-m "... and not network"`. A kernel's own tests run on the CPU, interpreted; its native run is a flow's cell. On a GPU the tier is a covering set (owner, 2026-11-11; row 5461): each model family that takes a distinct default route runs a model flow (`tests/test_gpu_flows.py`, `tests/model_flows.py`: its training step's gradients and its decode loop's logits on par with the reference path's against float64 truths, per GPU kind and precision, its bf16 attention flows under the lane's deterministic ops and as a user's process runs them), and a bare kernel cell stays only where no model flow reaches a route, family, launch kind or precision: each kernel matrix runs on a GPU over the combinations of its native axes, its GPU, kernel or launch, and precision, and over the cases a red found on a GPU (`tests/kernel_matrix.py`'s `native_cells`; rows 3522, 5268, 5404 and 5414 were fp32 summation orders a GPU alone showed); a route's shapes and hooks past those are the CPU's, interpreted and through the compile gate. A GPU part's prepare runs on its node's CPU first (`DEW_TIER_PREPARE=1`, `DEW_TIER_TRUTHS`): each flow computes every draw's float64 truth into the tier's store (`reference_error.stored_truths`) and compiles its programs for the node's GPU (`dew.training.ahead.compile_programs`), so its run computes no truth and compiles nothing, and a truth or program its prepare did not write is a red. A dependency or environment change (JAX, locks) is a change like any other: it lands in a train on the CPU CI, and the next native wave validates it, a red fixed forward at once (owner, 2026-10-25). The GPU gate runs that tier, the kernels' scoreboard rows ([kernel templates](kernel-templates.md)) and the performance gate (`tools/perf_gate.py`) on every gating type. A native wave runs the tier on every gating type; a change that lands on the CPU CI is validated by the next one. The GPU tier uses real checkpoints and representative shapes on each type it gates. Sharding and communication also run on multiple physical GPUs. A compile-only result does not establish runtime correctness. Target-specific FP8 and newer-device paths require the relevant hardware. TPU kernels need real TPU execution for their runtime claims.

## Numerical accuracy

Dew's outputs and gradients are measured from float64 truth: the same computation run in float64 on the same inputs. One gate, `tests/reference_error.py`, holds them by two checks and nothing else; a sampler's shares, which no float64 run computes, are the sampling gate's (below). Tests carry no per-operation knowledge; the gates hold it.

**Check 1's truth computes in float64** (`_of_float64`). The truth is the same computation in float64: the reference on the inputs widened, or the site's `truth_fn`. The gate establishes that before any verdict, from the truth alone: on the site's first draw every float leaf of the truth that holds a value is float64, and the program the truth's own calls trace computes no result narrower than float64 that a float output reads through floats, by JAX's primitives' facts. A narrow result read only by a comparison or as an integer (a dropout's float32 uniform against its rate) is a decision of the program's, the same in every arm and in the truth, and rounds no output; the chain runs through a call, a branch and a loop's step by their own outputs, a loop's carries to their fixed point. A stated rounding is kept: a cast to a narrower format, a format's own operation, and the moves of their entries (a quantized weight, a bf16 output). A constant or a literal is its exact value whatever its format, so a parameter left float32 under a float64 run is no rounding. A model of a fixed float32 dtype run on widened inputs computes in fp32 or rounds its answer to it: a second fp32 run, which equals the reference bit for bit, and Dew is judged against a truth no better than itself. Such a site is refused, naming the leaf (`NarrowTruth`), and takes a float64 clone of the model: the module, its parameters and every operation that feeds an output in float64. Where the narrow operation is a format's own arithmetic (a dequantizing division, a code's decode: the stored values are defined in that format), the truth says so at the site, value by value: it computes the value in float64 and declares the format's rounding (`stored_as`, a cast), which for one sum, difference, product, quotient or square root is the format's own correctly rounded result bit for bit inside its normal range (a backend's plain operation need not be: XLA's division by a constant, a GPU's division). The gate holds no list of exempt operations and exempts no file. A truth so widened that turns its site red has found an accuracy defect the false truth hid: the site's code is fixed, never the truth. A native kernel whose result an output reads is refused whatever its results' dtype: its body runs in its own format and is not read here, and a truth is the portable arithmetic. A truth the gate runs as given (NumPy, torch, a recording) traces no program and is held by its leaves alone; a cast only the truth takes (a round trip through float32 with no operation between) reads as a stated rounding and is not told apart. Each judgement's stage line records whether the reference equalled the truth on every first-stage seed (`exact`): the census of sites that measure no rounding.

**A port is held to its upstream.** A kernel or a route that ports another library's kernel (the selective template, mamba_ssm's `selective_scan_cuda`; a recurrence matrix cell's port) is held by check 1 to that upstream's own code at the cell's dtype, run live on the lane, or recorded over sized seeds where the upstream cannot run there, never to a transcription of it. An upstream that takes no packed row runs each document as its own sequence from a zero state, a shared operand's gradient the fp32 sum of the documents' pulls.

**A quantized computation's truth follows each arm's roundings** (`assert_as_exact`'s `followed`; the owner's choice of 2026-11-13, "Approve"). - the quantizers themselves are held bit for bit to the release's kernels;
- a whole quantized computation is held by check 1 with each arm against the float64 computation that rounds where that arm rounded: each arm returns its leaves and its roundings' decisions, each rounding's output as it computed it (`Rounded`), and its truth is `followed(decisions, *inputs)`, the arm itself untouched;
- a decision is no arm's error, but the value it rounds is: every rounding's input is a leaf of the site, held to the float64 value the followed truth rounds, so an arithmetic error before a rounding is charged where the decision it led to is followed.

**The sampling gate** (`assert_draws_as_declared` in `tests/sampling_gate.py`). **The learning gate** (`assert_learns` in `tests/learning_gate.py`). A learning claim (a trained model's samples take both modes at their places, training lowers the loss, the context helps the prediction) is about what training does on average, which no float64 run computes and one run measures with its own luck: over 320 runs of the flow-matching toy, a mode's mean missed its hand margin of 0.04 about one run in twenty-five, so the one-run check passed or failed by its seed. Over a site's declared units, each an independent training run or a trained model's independent draw, each claim is a contrast, positive where the unit meets it (an improvement's paired `before - 2 * after`; a value's margin less its departure, one side at a time, `within`), and each claim's mean contrast is held above zero by the one-sided t test at `LEVEL` 1e-9: a trainer whose units meet a claim exactly at its margin on average passes it once in a billion, where the one-run check passed it half the time. A two-sided margin is two one-sided claims because the margin less an absolute departure has a long left tail, which over eight units passed a claim at its margin more than twice as often as the t law says. A site's units are the fewest at which a trainer like a pilot of many more units fails a verdict with chance at most `FALSE_RED` 1e-4, by the noncentral t law (`units_for`); the gate's tests hold its verdicts' failures to that law at three sizes and effects. Both rates are the t law's: exact for normal contrasts, nominal for contrasts near normal, as a mean over many samples or a smooth function of one is from run to run; a contrast of rare large misses is not near normal, so a site's validation measures its contrasts' skew beside its verdicts, evidence for the approximation rather than a certificate of its tails. Validated at its first site, the toy's runs trained together on armada: the trainer passed 60 verdicts of 60 (36 at 56 runs, 24 at 64), its least t 10.1 against 7.0, its contrasts' skew within 0.35 at its weakest claims, and every verdict of four injected faults failed (the velocity target scaled by 0.8, a tenth of the training steps, a mode at a fifth of the data; a mode gone leaves a mode's mean undefined, and the site is refused). JEPA's context-dependence and the audio condition's loss drop, each a paired t over 64 units held by hand at 7.0, just past t's quantile at one in a billion on 63 degrees of freedom, are its verdicts at that quantile.

**Fast and accurate forms.** A kernel with a fast default and an accurate form one option away (attention's base-2 fold and fast backward, against `natural=True, accurate=True`; [kernel templates](kernel-templates.md#1-the-bar-with-the-comparison-defined)) holds each to its own contract, by `tests/test_attention_stability.py`'s families of adversarial inputs:

- **The accurate form** holds check 1 on drawn inputs and on every family, and keeps apart every pair of values the reference keeps apart: it merges no ties.
- **The default form** holds check 1 on drawn inputs. On every family it holds two things only: it is finite wherever the reference is finite, and it is exactly zero wherever the reference is (a row of no keys). Its error at the families' inputs is no claim, and where it ties values the reference keeps apart, those are its permitted ties, measured over 16 seeds of the plain-JAX mainloop as groups of a leaf's entries returned equal whose reference values spread past twice the reference's own error and two ulps more:
  - the output's, by the fold: at logits near 1e4 (1 group, 374 ulps), keys an ulp apart in bf16 (3, 8 ulps), and a sink and one key (1, 5 ulps);
  - dQ's, by FlashAttention's one bf16 product at the first D: at keys an ulp apart in bf16 (278 groups, 379 ulps);
  - dK's: at a small weight on a large value in bf16 (12, 8 ulps);
  - dV's, by the fold's recomputed weights: at keys an ulp apart in fp32 (100, 16 ulps).
- **Decode** holds the default's two claims on the families of a decode step.

A mainloop that composes the fold's guard (the plain-JAX one in its programs, `algebra.walked`, the Pallas-Triton one over its launches, `algebra.walked_launches`; a Mosaic mainloop must, before the stability suite runs it) holds the default's claims on every family. Every mainloop scales its rows' sums where they could pass fp32's largest (`algebra.SCALED_WALK`). The decode kernel does so in either form, so its default holds finiteness where its sums pass fp32's largest (the families the suite marks `overflows`), but it walks without the fold's reach, and fails the default's claims on the fold's other divergences at extreme inputs, the families the suite marks `folded=False`, which the accurate form alone runs. That is an open defect, not allowed behavior: the stability rule's guarantee of no NaN or infinity where the reference is finite stands, and the defect closes when the template's decode replaces that kernel (ledger 1637, the owner's ruling, 2026-10-25). The families: logits a ulp apart near 2^30 at scales below 1; a logit near fp32's largest, alone, with a sink or at scale 1/4, and one key; values near fp32's largest, over equal keys, beside a small, least-normal or subnormal column, or in a resumed state, and a sink near fp32's largest; in fp32, one weight carrying a row's output over values near fp32's largest; logits near 1e30; and two finite slices whose merge overflows, or a row that overflows beside one that does not. A tie is permitted only where the list above names it, and either list changes with the suite's families and measurements, in the same change.

The module's older assertions hold the comparisons not yet converted to check 1, and go once their last site moves.

The accurate form, measured the same way, tied at keys an ulp apart: dV in fp32, 48 groups of at most 16 ulps; the output in bf16, 3 groups of at most 8 ulps, each within check 1's 1.5× of the reference's error. Those ties break its no-merging contract above, which parity does not relax: they are an open defect of the accurate form, not permitted behavior, and the stability suite holds the accurate form to check 1 and its exact zeros, not yet to no merging (ledger 4205).

Investigate a failure in Dew, the reference arm or the gate. Do not change the reference to match Dew, exclude failing positions or gradients, or compare only argmax when logits disagree. The library-arm rule above is the only permitted bound exception.

The suite holds a CPU to wide arithmetic, a test setting and not a user option: `tests/lane_environment.py` sets `DEW_WIDE_CPU_ARITHMETIC=1` (`dew.nn.precision.WIDE_CPU_ARITHMETIC`), under which a CPU's float32 products follow the accumulation policy `dew.nn.precision` states with its boundary (the dot family sums in float64, convolutions keep XLA's fp32 sum), a loop's running sum of those products is compensated so it rounds once, and a float32 row reduction (the vocabulary row's fused logsumexp) is taken in float64 and rounded once (`dew.nn.precision.widened_reduction`); a float64 division is the backend's plain division, the setting or not. A library process sets nothing: every platform takes the plain product, a CPU's float32 sums XLA's own (row 5448). Within the suite, a program that wants a CPU's fp32 sums, a reference standing for an accelerator's arithmetic, runs under `jax.default_matmul_precision("F32_F32_F32")` (`FP32_SUMS`), which takes the fp32 product. What the suite's processes cannot show is any program a library process builds outside check 1's arms (a training step's shapes and placements, a plan's footprint, a route, a cache's bits), so a set of the suite's own tests, one for each class a user's arithmetic has broken, runs again in every train in a child process with the suite's devices and none of its arithmetic (`tests/test_users_process.py`, `lane_environment.users_process`): a command-line run whose attention the algebra pass misread, a crash on an Explicit data axis in the float32 product path and a partitioning that gathered what the float64-summing program split were all green in the suite's processes and red there (rows 5438, 5422, 5427); each class's test joins the set with its fix.

The committed generator uses the reference's public interface. Kernel qualification records forward, backward and forward-mode behavior where the consuming objective needs it.

**Layout invariance.** Raw random bits, and what exact operations alone derive from them (uniforms, bit-compare masks such as dropout's), are bit-identical on every layout. Floats derived through rounding chains (normals, Gumbel noise, initial weights) are held equal across layouts by check 1 of `tests/reference_error.py`. A discrete result taken from them, such as a categorical sample by the argmax of Gumbel noise plus logits, can flip near a tie, and its check says so. Every other exact contract stays exact: checkpoint and resume, caches, serialization, and the same program run twice in deterministic mode. A float claimed equal across layouts or placements is bit for bit only where both run one program on the same values (the same compiled HLO in two processes, a resumed run); where the two compile to different programs it is held by check 1, as any float two programs compute is (above).

## Property tests

Hypothesis is for property, metamorphic and fuzz tests: an invariant held over drawn inputs (an operation's algebraic law, an equivalence between two forms of one computation, a parser or planner's behavior on generated input). It is not an accuracy gate. A property test that judges numerics draws its shapes or configuration from Hypothesis and holds each with `assert_as_exact`, whose seeds draw the values; it carries no tolerance of its own.

The suite's profile, `dew` (tests/conftest.py), draws the same examples on every run, so a red reproduces anywhere; keeps no example database, and stores nothing in the checkout (its storage goes under the system temp directory unless `HYPOTHESIS_STORAGE_DIRECTORY` is set); and runs 50 generated examples, each under a soft 2 s deadline. Those are workload targets, not a wall-time bound: explicit examples, discarded draws and shrinking run beyond them, and the deadline is checked after an example runs. A test whose examples compile (a new shape each draw) sizes its own `settings` deadline and count from its measured runtime, within a test's 120 s with room for generation and shrinking.

A failure shrinks to a minimal example. That example joins the test as a regular case (`@example`, or a test of its own), so the defect stays covered whatever later strategies draw.

## Tests must catch a defect

CONTRIBUTING.md owns behavioral test authoring, red-before/green-after proof and external-boundary mocks. Exercise interruption, corruption and admission failures with the code under test unchanged.

Check resource release and primary-error preservation through the same lifecycle.

Run the scenario suite with branch coverage (coverage.py) on armada and publish the per-module report.

Branch coverage directs scenario settings. Uncovered code that a real use case reaches gets a scenario setting. Uncovered code that no real use case reaches is a deletion candidate, decided by the user's surface review. A unit test whose lines the scenarios already cover, and which asserts nothing a scenario doesn't, is deleted. Existing flow files compose these scenarios through the same execution helpers, without a second flow framework.

## What the suite costs

`tests/test_durations.json` is the CPU plan's weights and nothing else: each test's seconds as the CPU suite's last green rows observed it, by which the plan cuts a file into tasks (`tools/armada/ci.py durations` folds it from main's CI). A test the CPU suite skips, one marked for a GPU, weighs its skip there, a thousandth of a second for a flow that trains for minutes on its device; a check-1 site's entry is its judge's pooling, not its draws. So the file is no ledger of cost. What the CPU suite costs is read from a run: its rows' seconds and its sites' map tasks, which armada times. What a GPU test costs is read from its tier's receipts, each row's own tests' seconds on its device.
