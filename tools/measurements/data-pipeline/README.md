# Data-pipeline migration receipts

These scripts produced the evidence for the move to `Pipeline` recipes: what the old loaders read. Each one is pinned to the revisions it names, so it reproduces that evidence and is not a maintained tool or a CI gate. Run them from the repository root, with Dew installed from the checkout. Their `r2://` pins name Dew's own data bucket, which public Dew does not reach. Reading them needs the dew-ops `r2` filesystem adapter, and the publishing steps need write access through it.

| File | Baseline | Purpose | Reproduction |
| --- | --- | --- | --- |
| `data_oracle.py`, `golden_records.py` | Dew `7ad0d4079` | Records what each old loader read from synthetic records, at 0 and 2 workers and 1 and 2 shares. `data_oracle.py` downloads the baseline and the capture script as Dew last held it (`LEGACY_SCRIPT`, which drives the baseline's loader API), and runs the script inside the baseline. `golden_records.py` holds copies of the capture's digest and input writers for the golden test, which the fixture holds to the capture's. The gzipped output is `tests/fixtures/golden/loaders-7ad0d4079.json.gz`, which `tests/test_pipeline_golden.py` reads. A regeneration reproduces the cases that test pins to 7ad0d4079. It does not reproduce the `images_*` cases, which pin Dew's public image steps: they were re-recorded from Dew where its random stages' seeds changed on purpose (`d9d198d35b6`: each stage seeded by its depth; `ad17441ed34`: by the count of random stages before it), with augmentation off proven unchanged against the baseline each time. Nor does it reproduce the fields the test's docstring names as Dew's own (packed text's piece targets, `Coordinates.firsts` and `finals`, the data phase). | `python tools/measurements/data-pipeline/data_oracle.py --output loaders-7ad0d4079.json` |
